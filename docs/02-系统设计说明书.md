## 1 总体架构

系统采用**前后端分离的三层架构**（表现层 / 应用层 / 数据层）：

└───────────────────────────┬───────────────────────────────────┘
                            │ HTTP / JSON（JWT Bearer）
┌───────────────────────────▼───────────────────────────────────┐
│  应用层   Spring Boot 3.5（Java 21）                            │
│  ├ 安全       security（无状态 JWT + 方法级鉴权）               │
│  ├ 知识库     module.kb       条目 / 分类 / 标签 / 附件         │

## 2 关键技术选型与理由

### 2.1 全文检索：MySQL ngram 全文索引（而非 Elasticsearch）

| 维度 | MySQL 全文索引（ngram） | Elasticsearch |
|---|---|---|
| 部署复杂度 | 无额外组件 | 需独立集群 |
| 中文支持 | ngram 二元切分，开箱可用 | IK 分词器，需额外维护 |
| 与业务数据一致性 | **同库同事务，天然一致** | 需同步管道，存在延迟窗口 |
| 适合规模 | 十万级文档 | 千万级以上 |

**决策：选用 MySQL 8.0 全文索引 + ngram 解析器。** 理由：

1. 本课题数据规模在万级，MySQL 完全胜任，实测平均检索耗时约 18 ms 量级；
2. 无需引入额外中间件，降低部署与答辩演示的风险；
3. 索引与业务数据在同一事务内更新，**不存在主库与索引不一致的窗口**；
4. ngram 把中文切成二元组，「软件测试」被切为「软件」「件测」「测试」，
   因此查询「软件测试」或「测试」都能命中。

**局限性及补偿：** ngram 索引体积偏大；不支持同义词扩展（由本体的查询扩展功能补偿）；
单字查询不命中（`ngram_token_size = 2`，在界面明确提示）。

### 2.2 向量存储：BLOB + 内存余弦比对（而非向量数据库）

向量以 `float32` 小端字节序列存入 `rag_chunk.embedding`（`MEDIUMBLOB`），检索时在内存中
计算余弦相似度。理由：

1. 分块规模为百级至千级（实测 60 条条目 → 164 个分块），单次全量比对的开销远小于
   引入向量数据库带来的部署与运维成本；
2. 向量与分块正文同库同表，便于「切换模型后重建」时的事务性删除与重建；
3. 保留 `dim` 与 `embed_model` 字段，使向量**自描述其来源**，可支持不同模型向量的分组比对。

当数据规模增长到十万级分块以上时，该方案应替换为近似最近邻（ANN）索引。

### 2.3 为什么采用混合检索

两条通道的强弱互补：

| 通道 | 优势 | 劣势 |
|---|---|---|
| 向量通道（余弦相似度） | 擅长「问法与原文用词不同」的语义匹配 | 精度有限，易召回泛泛而谈的块 |
| 关键字通道（ngram 全文索引） | 词面命中精确，在术语密集语料上更可信 | 无法处理同义改写，易漏召回 |

**融合方式：倒数排名融合（RRF）**，对每条通道的排名取 `1 / (k + rank)` 相加，`k` 取 60。
RRF 只依赖排名、不依赖两侧分数可比，天然规避了「相似度 0.83 与 BM25 分 12.4 如何相加」
的问题。本系统对关键字通道的融合得分额外乘以 **1.15** 的权重，因为在课程知识库这类
术语密集的语料上，词面命中往往更可信。

### 2.4 为什么 RAG 必须能降级

RAG 依赖两个外部能力：向量化与文本生成。二者均可能因**未配置 API Key、网络不可用、
限流或额度耗尽**而失败。若不做降级，系统将在无网络环境（例如答辩现场）下完全无法演示问答。

**降级策略分两级：**

| 环节 | 主用能力 | 降级路径 |
|---|---|---|
| 向量化 | 在线语义向量模型（OpenAI 兼容 `/embeddings`） | 本地哈希向量模型（离线、零依赖、词汇级匹配）；单次调用失败亦自动降级 |
| 生成 | 在线大模型（OpenAI 兼容 `/chat/completions`） | 离线抽取式回答 `ExtractiveAnswerBuilder`：从检索片段中抽取最相关句子、按来源编号列出，不生成新内容，零幻觉 |

生成环节的降级**不静默替换**，而是返回 `degraded=true` 与降级原因，界面明确标注；因为
「降级」在此意味着回答形态的改变，必须显式告知用户。

## 3 核心流程时序

### 3.1 RAG 问答（六步流程）

对应 `rag.module.RagService.ask()`：

```text
用户问题
  │
  ├─(1) 本体查询扩展 expandQuery()
  │      实体链接识别问题中的知识点 → 沿本体关系（SUB_CLASS_OF/PART_OF/
  │      PREREQUISITE_OF/RELATED_TO）扩展相邻概念 → 拼入检索串
  │
  ├─(2) 混合检索 HybridRetriever.retrieve(query, topK×2, scope)
  │      ├ 向量通道：余弦相似度取 Top-20（跳过维度不匹配的块）
  │      └ 关键字通道：MySQL ngram 全文索引取 Top-20
  │      └ RRF 融合：Σ 1/(k+rank)，k=60，关键字通道 ×1.15
  │
  ├─(3) 上下文组装 buildContexts()
  │      按块去重、跳过归档条目、按条目组织，加【来源 N】编号，截断至 topK 块
  │
  ├─(4) 生成 generate()
  │      ChatService.tryComplete()  → 在线大模型
  │         └ 不可用/失败 → ExtractiveAnswerBuilder 离线抽取式回答
  │
  ├─(5) 落库 saveMessage()
  │      会话、消息、引用（JSON）、检索过程元数据（JSON）、模型标识、耗时
  │
  └─(6) 返回 AnswerDTO
         回答 + 引用列表 + 检索元数据（各通道候选数、排名、融合得分、耗时）
```

### 3.2 条目保存的建版判定

对应 `cms.module.VersionService.autoSnapshot()` 与 `VersionPolicyService.evaluate()`：

```text
保存条目 KnowledgeItemService.update()
  │
  ├─ 累加 item.changeCount，更新 plain_text 与关键词
  ├─ versionService.autoSnapshot(item, changeLog)
  │     │
  │     ├─ policyService.evaluate(item)
  │     │     解析生效策略：ITEM → CATEGORY → GLOBAL → 内置默认
  │     │     计算 days（距上次快照）与 pendingChangeCount（累计修改）
  │     │     due = (days ≥ intervalDays)  或  (changeCount ≥ minChangeCount)
  │     │
  │     ├─ due == false → 返回 null，不建版
  │     │
  │     └─ due == true → doSnapshot()
  │           ├─ 计算正文 MD5；与上一版本一致且非发布 → 跳过（不产生空版本）
  │           ├─ 版本号 = maxVersionNo + 1
  │           ├─ 保存完整正文快照 + 概念/标签快照 + 字符增删量
  │           ├─ 推进 item.versionNo，重置 changeCount，刷新 lastSnapshotAt
  │           └─ pruneIfNeeded：版本数超过 max_versions 时淘汰最旧的
  │
  └─ 发布事件 ItemChangedEvent.saved(id)  →  RAG 模块异步重建索引
```

**显式建版（无条件，不受阈值约束）：** 手工创建版本（须填写说明）、发布、回滚。
回滚前额外为「当前状态」留存一份快照，使回滚动作本身可撤销。

### 3.3 检索的「召回 + 重排序」两条通道

对应 `search.module.SearchService.search()`：

```text
检索请求（带关键词）
  │
  ├─ 关键词长度截断至 120 字符；拆分为查询词集合
  │
  ├─ 通道一：tryFulltext()  —— 数据库只负责「召回」
  │     ├ 放大 6 倍取候选（按页深线性放大，上限 300 条），
  │     │   避免数据库相关度偏好长文档导致标题精确命中者进不了候选池
  │     └ 应用层重新打分 buildHits()：
  │           字段命中率（标题×0.80 + 摘要/关键词×0.20）× 0.65
  │         + 全文相关度（归一化）× 0.25
  │         + 热度（log1p(viewCount)/log1p(500)）× 0.10
  │         + 标题完整包含查询串的额外奖励 0.20
  │     └ 排序后在候选池内本地分页
  │
  ├─ 通道二（全文未命中/不可用）：fallbackLikeSearch() —— 模糊匹配降级
  │     合并正文关键词命中与附件正文命中，用启发式打分（标题>摘要>正文）排序后本地分页
  │
  └─ 通道三（高级检索/无关键词）：conditionSearch() —— 条件过滤
        按分类（含子分类）、类型、标签、知识点、作者、时间过滤后排序

后处理：
  ├─ weakMatch 判定：无任何结果在标题/摘要命中查询词 → 标记为弱匹配（不隐藏）
  ├─ 附加本体知识点（linkedConcepts）便于沿知识结构继续探索
  └─ 无结果或弱匹配 → 生成零结果建议；记录检索日志
```

## 4 设计模式应用

| 模式 | 应用位置 | 解决的问题 |
|---|---|---|
| **策略模式** | 接口 `rag.embedding.EmbeddingModel`（实现：`LocalHashingEmbedding`、`OpenAiEmbedding`）；接口 `rag.chat.ChatModel`（实现：`OpenAiChatModel`） | 本地向量模型与在线向量模型可互换；掩蔽外部模型差异，支持运行时降级 |
| **观察者模式** | 领域事件 `common.event.ItemChangedEvent` + `@EventListener`（`RagIndexService.onItemChanged`） | 内容变更后解耦地重建检索索引，`kb` 与 `rag` 模块互不直接依赖 |
| **门面模式** | `rag.RagService.ask()` | 把「扩展 → 检索 → 组装 → 生成 → 落库」五步收敛为一个入口，隐藏内部协作 |
| **模板方法** | `SearchService` 的 `tryFulltext` / `fallbackLikeSearch` / `conditionSearch` | 统一「尝试主通道 → 失败降级」的骨架，各通道替换具体实现 |
| **单例 + 依赖注入** | 所有 `@Service`、`@Component` 由 Spring 容器管理 | 无状态服务共享，避免重复构造 |
| **代理（Spring AOP）** | `@Transactional`、`@Async`、`@PreAuthorize` | 声明式事务、异步与鉴权；注意自调用不经过代理（见《测试报告》缺陷①） |

## 5 接口设计

### 5.1 统一响应结构

所有 REST 接口返回统一的 `ApiResponse<T>`：

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "timestamp": 1760000000000
}
```

**约定：** `code == 0` 表示成功，非 0 为业务 / 系统错误码；前端只需判断 `code` 与 `message`，
`data` 为业务数据。前端 `api/request.js` 统一拦截并解包 `data`。

### 5.2 状态码约定

错误码字典见 `common.ErrorCode`：

| code | 含义 | 典型场景 |
|---|---|---|
| `0` | 成功 | — |
| `400` | 参数错误 | 校验失败、非法参数 |
| `401` | 未认证 | 未登录、令牌过期、口令错误 |
| `403` | 无权限 | 越权访问（如浏览者创建条目） |
| `404` | 资源不存在 | 条目 / 会话 / 版本不存在 |
| `409` | 状态冲突 | 编码重复、非法状态流转 |
| `1000` | 通用业务错误 | 兜底 |
| `1001` | 文件上传错误 | 类型 / 大小超限 |
| `1002` | 检索错误 | — |
| `1003` | RAG 错误 | — |
| `500` | 服务器内部错误 | 未捕获异常 |

### 5.3 鉴权方式

- **方式：** 无状态 JWT（HS256）。登录成功后返回令牌，客户端在请求头携带
  `Authorization: Bearer <token>`。
- **有效期：** 720 分钟（12 小时）；签发者 `njupt-kms`；密钥要求 ≥ 32 字节
  （生产环境应通过环境变量 `KMS_JWT_SECRET` 覆盖）。
- **放行策略：** `SecurityConfig` 中精确放行登录 / 注册、公开只读接口（检索、本体图谱、
  条目列表、文件预览、版本查询等），其余请求需认证。
- **授权粒度：** 方法级 `@PreAuthorize`，角色编码即权限字符串（`hasRole('ADMIN')` 等）。

### 5.4 接口组织

接口按模块划分为 12 个控制器（`module.*.controller`），主要分组如下：

| 分组 | 前缀 | 说明 |
|---|---|---|
| 认证 | `/api/auth` | 登录、注册、当前用户、改密、改资料 |
| 用户 | `/api/users` | 用户 CRUD、角色列表 |
| 知识库 | `/api/knowledge` | 条目分页 / 详情 / 管理端 / 创建 / 更新 / 发布 / 归档等 |
| 分类 | `/api/categories` | 列表、树、增删改 |
| 标签 | `/api/tags` | 列表、热门、联想 |
| 本体 | `/api/ontology` | 概念、关系类型、关系、图谱、邻域、推理、统计、实体链接 |
| 检索 | `/api/search` | 统一检索、高级检索、联想、热搜、统计 |

## 6 前端设计

### 6.1 路由表

采用 **hash 路由**（`createWebHashHistory`），使前端可部署到任意静态服务器而无需服务端
rewrite 配置，对答辩演示环境更友好。全局前置守卫依据 `meta.public` / `meta.requiresAdmin` /
`meta.requiresEdit` 与用户状态重定向。

### 6.2 布局

`layout/AppLayout.vue` 提供统一外壳：**左侧分组导航**（`main` 主功能区 / `manage` 管理区 /
`admin` 管理端，导航项由路由的 `meta.group` 与 `meta.icon` 驱动）+ **顶栏**（面包屑、
用户菜单），内容区为 `<router-view>`。菜单按角色动态显隐，实现「界面即权限」。

### 6.3 组件复用

| 组件 | 复用点 |
|---|---|
| `EChart.vue` | 所有图表的渲染外壳，统一处理主题、尺寸与销毁；负责高度单位归一化 |
| `ChartCard.vue` | 「标题 + 图表 + 等价数据表」的卡片外壳，在多个看板与检索分析页复用 |
| `KnowledgeCard.vue` | 知识条目的卡片展示，在列表、检索结果、我的内容、归档等处复用 |
| `MarkdownView.vue` | 条目正文的 Markdown 渲染，在详情与版本比对处复用 |
| `StatTile.vue` | 看板的统计磁贴，统一数值与标签的排版 |

### 6.4 配色与可访问性

设计上把「可访问性」当作硬约束而非装饰：

1. **分类色板经过色觉缺陷可辨识性校验。** 分类色序固化在 `utils/echartsTheme.js` 的 `SERIES`
   与 `styles/index.scss` 的 `--series-N` 中，相邻色对在**色觉缺陷模拟（protan / deutan / tritan）
   下 ΔE ≥ 9、正常视觉 ΔE ≥ 19**，保证色觉障碍用户同样能区分。知识域的配色同样遵循该校验
   （软件工程 `#2a78d6`、数据库 `#1baf7a`、知识管理 `#eb6834`）。
2. **信息不依赖颜色单一通道。** 图谱中的边除颜色外**同时带文字标签**；图表配图例。
3. **图表配「显示数据表」等价视图。** `ChartCard.vue` 为每张图表提供一键切换的数据表，
   保证「图表用颜色传达的差异」在色觉障碍或黑白打印场景下信息始终可达。
4. **墨色后退、数据前进。** 图表外壳（网格线、坐标轴、文字）统一使用中性墨色，只有承载
   数据的图元使用分类色，使读者注意力自然落在数据上。
5. **危险操作二次确认。** 删除、回滚、归档等操作均需二次确认；空状态、加载态与错误提示
   齐备。

## 7 部署结构

### 7.1 端口与目录

| 项 | 值 | 来源 |
|---|---|---|
| 后端端口 | `8080` | `server.port` |
| 前端开发端口 | `5173` | Vite 默认 |
| 数据库 | `localhost:3306`，库名 `kms` | `spring.datasource.url` |
| 后端文件存储根目录 | `../storage`（相对后端进程工作目录） | `kms.storage.root` |
| 文件存储布局 | `<root>/yyyy/MM/<uuid>.<ext>` | `FileStorageService` |
| 数据库脚本 | `backend/src/main/resources/db/schema.sql` | 20 张表，可重复执行 |
| 接口文档 | `/swagger-ui.html` | `springdoc` |

**存储布局说明：** 上传文件按**年月分目录**存储，避免单目录文件过多导致的操作系统
目录项性能下降；文件名使用 UUID，原始文件名保留在数据库 `kb_attachment.file_name` 中。

### 7.2 环境变量（可选覆盖）

| 变量 | 默认值 | 用途 |
|---|---|---|
| `KMS_DB_USERNAME` | `root` | 数据库用户名 |
| `KMS_DB_PASSWORD` | （见配置） | 数据库口令 |
| `KMS_JWT_SECRET` | 内置开发密钥 | JWT 签发密钥（生产务必覆盖） |
| `KMS_STORAGE_ROOT` | `../storage` | 文件存储根目录 |
| `KMS_EMBEDDING_PROVIDER` | `local` | 向量模型：`local` / `openai` |
| `KMS_EMBEDDING_BASE_URL` | `https://api.siliconflow.cn/v1` | 在线向量服务地址 |
| `KMS_EMBEDDING_API_KEY` | 空 | 在线向量服务密钥 |
| `KMS_EMBEDDING_MODEL` | `BAAI/bge-m3` | 在线向量模型名 |
| `KMS_CHAT_PROVIDER` | `openai` | 生成模型：`none` / `openai` |
| `KMS_CHAT_BASE_URL` | `https://api.deepseek.com/v1` | 在线生成服务地址 |
| `KMS_CHAT_API_KEY` | 空 | 在线生成服务密钥（为空则走离线抽取式回答） |
| `KMS_CHAT_MODEL` | `deepseek-chat` | 在线生成模型名 |

### 7.3 启动方式

```text
1. 初始化数据库：执行 backend/src/main/resources/db/schema.sql（创建 kms 库与 20 张表）
2. 启动后端：在 backend 目录执行 mvn spring-boot:run
   —— 首次启动时若表为空，自动导入本体（107 概念 / 183 关系）与演示数据
      （4 用户 / 18 分类 / 30 标签 / 60 条目 / 11 附件），并创建默认全局版本策略
3. 构建索引：管理员登录 → 「检索索引」页 → 重建索引（构建 164 个分块）
4. 启动前端：在 frontend 目录执行 npm install && npm run dev，访问 http://localhost:5173
5. 环境自检：python scripts/smoke_test.py（接口冒烟）、node scripts/ui_check.mjs（界面检查）
```

**运行期可调参数（应用配置）：** 全文检索 `kms.search.*`（最大页大小 100、摘要片段 200 字符、
高亮标签 `<mark>`）；RAG `kms.rag.*`（分块 420 字符 / 重叠 80、top-k 6、各通道 20、RRF k=60、
本体扩展开关与上限 6、历史轮数 3）；版本 `kms.version.*`（默认天数 1、次数 5、保留 50、
自动快照开启）。
