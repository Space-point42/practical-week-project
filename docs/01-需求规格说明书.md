## 1 引言

### 1.1 编写目的

本文档面向以下读者：

| 读者 | 关注点 |

| 指导教师 / 验收教师 | 需求是否覆盖任务书要求、是否可验证 |

| 测试人员 | 由需求导出测试用例的输入 |
| 后续维护者 | 系统「为什么这样设计」的背景 |

本文档定义系统**做什么**（功能需求）与**做到什么程度**（非功能需求），不描述**如何实现**；
实现方式见《系统设计说明书》与《数据库设计说明书》。

### 1.2 项目背景与范围

知识管理系统（Knowledge Management System，KMS）用于帮助组织与个人有效地创建、分享、
应用和维护知识。本系统面向《专业课程设计II》课程场景，围绕**软件工程**与**数据库原理**
两大理论支柱以及**知识管理与智能检索**这一课题自身的技术领域，构建一套可检索、可问答、
可版本回溯的知识资产管理系统。

**范围界定：**

- **包含**：知识资产的组织与检索、知识本体的建模与推理、全文检索与检索增强问答（RAG）、
  内容的多格式管理与版本管理、用户权限与审计统计。
- **不包含**：跨组织知识共享、内容创作协同编辑、移动端原生应用、独立的搜索引擎中间件部署。
- **数据边界**：全部业务数据存储于 MySQL 8.0 单库（`kms`），共 20 张表；文件按年月目录存储于
  文件系统。

### 1.3 术语定义

| 术语 | 英文 / 编码 | 含义 |
|---|---|---|
| 知识资产 | Knowledge Asset | 具有复用价值的文档、报告、论文、视频等内容实体，对应 `kb_item` 表 |
| 知识条目 | Knowledge Item | 知识资产在系统中的一条记录，含标题、摘要、正文、附件等 |
| 知识本体 | Ontology | 对领域知识的**显式、形式化**描述，由概念、关系、属性、公理四要素构成 |
| 概念 / 知识点 | Concept | 本体中的类，对应 `ont_concept` 表；本系统共 107 个 |
| 三元组 | Triple | `(主语, 谓词, 宾语)` 形式的一条知识断言，对应 `ont_relation` 表 |
| 分类 | Category | 按主题层次组织知识的**管理视角**结构，对应 `kb_category` 表 |
| 标签 | Tag | 表达内容交叉特征的自由词，对应 `kb_tag` 表 |
| 全文检索 | Full-text Search | 对文本全部内容建立索引并按相关度排序返回结果的检索方式 |
| 本体覆盖率 | Ontology Coverage | 已被知识条目标注过的知识点占全部知识点的比例 |
| RAG | Retrieval-Augmented Generation | 检索增强生成：先检索相关知识，再由大模型基于检索结果作答 |
| RRF | Reciprocal Rank Fusion | 倒数排名融合，混合检索中合并多路排名的方法 |
| 版本策略 | Version Policy | 决定「何时为条目建立新版本快照」的规则，以天数与修改次数为阈值 |
| 快照 | Snapshot | 某一时刻内容的**完整**副本，而非增量补丁 |
| 实体链接 | Entity Linking | 从文本中识别出本体概念的算法 |

## 2 总体描述

### 2.1 系统定位

本系统是一套 **B/S 架构、前后端分离**的 Web 应用：

- **前端**：Vue 3 + Element Plus + ECharts，使用 hash 路由，编译后可作为静态资源部署。
- **后端**：Spring Boot 3.5（Java 21），按业务域划分为 9 个模块（`kb`、`ontology`、`search`、
  `rag`、`cms`、`archive`、`audit`、`stats`、`user`），对外提供 REST 接口。
- **数据库**：MySQL 8.0，字符集 `utf8mb4`，中文全文检索使用 **ngram 解析器**（`ngram_token_size = 2`）。

系统以「知识的内在结构」为核心组织原则：既通过**分类树**表达管理视角的归属，也通过
**本体（概念层次 + 语义关系）**表达知识视角的结构，二者互补。

### 2.2 用户角色

系统采用基于角色的访问控制（RBAC），角色编码存于 `sys_role.code`，共三类：

| 角色 | 编码 | 主要权限 | 典型操作 |
|---|---|---|---|
| 管理员 | `ADMIN` | 全部权限 | 用户管理、本体维护、版本策略配置、检索索引重建、审计日志查阅 |
| 编辑 | `EDITOR` | 内容创作与发布 | 创建 / 编辑 / 提交 / 发布 / 归档知识条目，管理版本，回滚 |
| 浏览者 | `VIEWER` | 只读与交互 | 检索、浏览、下载、知识图谱探索、RAG 问答、点赞 |

权限以方法级鉴权实现（`@PreAuthorize("hasRole('ADMIN')")` 等）。**公开读取类接口匿名可访问**
（如知识条目列表、本体图谱、检索），**写操作必须认证**。演示账号见附录 A。

### 2.3 运行环境

| 层次 | 组件 | 版本 / 说明 |
|---|---|---|
| 服务端运行环境 | JDK | Java 21（开发与验收环境实测使用 Java 23 亦可运行） |
| 构建工具 | Maven | 3.9 及以上 |
| 数据库 | MySQL | 8.0.42 |
| 前端运行环境 | Node.js | 24 |
| 浏览器 | Chromium / Edge / Chrome | 支持 ES2020 的现代浏览器 |
| 界面测试工具 | Playwright（Chromium 驱动） | 用于自动化界面检查与截图 |
| 接口测试工具 | Python 3（仅标准库） | 运行 `scripts/smoke_test.py` |

**服务端口：** 后端 `8080`，前端开发服务器 `5173`。均支持通过环境变量或启动参数覆盖。

### 2.4 设计约束与假设

| 类型 | 内容 |
|---|---|
| 约束 | 数据库须为 MySQL 8.0（依赖 `WITH PARSER ngram` 全文索引与 `utf8mb4`） |
| 约束 | 中文全文检索的最小切分单位为 2 个字符，即**单字查询不会命中** |
| 约束 | 在线大模型 / 在线向量模型为可选依赖，未配置时系统须能完整降级运行 |
| 假设 | 数据规模在万级条目以内，单库单实例即可支撑 |
| 假设 | 用户通过局域网或本机访问，暂不设计跨区域高可用部署 |

## 3 功能性需求

需求以「系统应……」的句式描述，编号规则为 `FR-模块序号.子项序号`。每条需求在
第 6 节的需求追踪矩阵中映射到实现模块与测试用例。

### 3.1 FR-1 知识库

> 溯源：任务书题目1「知识库：存储……各种知识资产，如技术报告、文档、论文、视频等。允许用户
> 搜索、浏览、分类和归档知识内容。应注重知识的内在结构（如层次关系）。」

| 编号 | 需求描述 |
|---|---|
| FR-1.1 | 系统应支持知识条目的创建、编辑、删除（逻辑删除）与恢复。 |
| FR-1.2 | 系统应支持为知识条目指定资产类型，类型应至少覆盖 `DOCUMENT`（文档）、`REPORT`（技术报告）、`PAPER`（论文）、`VIDEO`（视频）、`IMAGE`（图片）、`CODE`（代码）、`MINDMAP`（思维导图）、`OTHER`。 |
| FR-1.3 | 系统应支持**多层级分类**（分类树），分类应支持父子层次与物化路径查询。 |
| FR-1.4 | 系统应支持为条目设置 2~5 个标签，并按标签的使用热度排序展示。 |
| FR-1.5 | 系统应支持上传多格式附件（文档 / 图片 / 音视频），并应支持同一格式族内的常见扩展名。 |
| FR-1.6 | 系统应自动抽取文档类附件（PDF / Word / Excel / PPT 等）的正文，且抽取的正文应可被全文检索命中。 |
| FR-1.7 | 系统应支持为条目标注本体概念（知识点），标注来源应区分 `MANUAL`（人工）与 `AUTO`（自动抽取）。 |
| FR-1.8 | 系统应支持按知识点反查关联的知识条目。 |
| FR-1.9 | 系统应支持条目的归档与恢复；归档条目应保留正文、附件与版本历史，但移出常规检索与问答召回范围。 |
| FR-1.10 | 系统应记录并展示条目的浏览次数、点赞次数、下载次数与当前版本号。 |

### 3.2 FR-2 搜索引擎

> 溯源：任务书题目1「搜索引擎：快速定位知识库中的相关内容。支持全文搜索、高级搜索和
> RAG 问答功能。」

| 编号 | 需求描述 |
|---|---|
| FR-2.1 | 系统应支持全文检索，检索范围应覆盖条目标题、摘要与正文。 |
| FR-2.2 | 系统应返回**按相关度排序**的检索结果，排序应综合考虑字段命中率、全文相关度与内容热度。 |
| FR-2.3 | 系统应在结果中对命中词进行高亮，并给出包含命中词的正文摘要片段。 |
| FR-2.4 | 系统应支持高级检索，组合条件应至少包含：分类（含子分类）、资产类型、标签、知识点、作者、创建时间区间。 |
| FR-2.5 | 系统应支持按「相关度 / 最新 / 最热 / 最多点赞」切换排序方式。 |
| FR-2.6 | 系统应支持检索词联想，联想来源应包括历史检索词、知识点名称与条目标题。 |
| FR-2.7 | 系统应统计并展示热搜词与零结果检索词。 |
| FR-2.8 | 系统应在检索无结果或仅弱匹配时给出可操作的替代建议，而**不应**返回空白页。 |
| FR-2.9 | 系统应支持 RAG 问答：先检索知识条目，再由生成模型基于检索结果作答。 |
| FR-2.10 | RAG 回答应标注引用来源（来源编号、条目标题、片段与得分），并支持从引用跳转到原文。 |
| FR-2.11 | 系统应展示 RAG 的检索过程元数据，包括：命中的知识点、本体扩展出的概念、各召回通道的候选数与排名、融合后的得分。 |
| FR-2.12 | 当知识库无相关内容时，系统应如实说明「资料未涵盖」，而不得编造答案。 |
| FR-2.13 | 当未配置或无法调用生成模型时，系统应自动降级为离线抽取式回答，并向用户明确提示处于降级模式。 |
| FR-2.14 | 系统应记录检索行为日志（关键词、检索类型、结果数、耗时），供检索分析与优化使用。 |

### 3.3 FR-3 知识本体

> 溯源：任务书题目1「应注重知识的内在结构（如层次关系），用本体对知识的逻辑结构进行建模，
> 本体需覆盖至少 20 个知识点、5 种关系。」

| 编号 | 需求描述 |
|---|---|
| FR-3.1 | 系统应以本体建模《专业课程设计II》相关知识的逻辑结构，**知识点数量应不少于 20 个**（实际实现 107 个）。 |
| FR-3.2 | 系统应支持**不少于 5 种语义关系**（实际实现 7 种：上下位、组成、先修、相关、应用于、产出、近义）。 |
| FR-3.3 | 系统应以概念层次树表达知识的分类归属（`parent_id` + 物化路径 `path`）。 |
| FR-3.4 | 系统应以三元组 `(源概念, 关系类型, 目标概念)` 表达概念间的语义关系，并支持为关系赋予权重（0~1）与自然语言说明。 |
| FR-3.5 | 系统应支持概念、关系类型与关系实例的增删改查，内置元素应不可删除。 |
| FR-3.6 | 系统应支持知识图谱可视化，节点应按知识域着色、按关联内容量编码大小，边应区分关系类型并提供可筛选的图例。 |
| FR-3.7 | 系统应支持沿指定关系类型的**本体推理**，如沿先修关系（`PREREQUISITE_OF`）推导学习路径。 |
| FR-3.8 | 系统应支持**实体链接**：从一段文本中识别出所涉及的本体概念（长词优先、别名归一）。 |
| FR-3.9 | 系统应支持**查询扩展**：检索与问答时，沿本体关系将命中概念的相邻概念拼入检索串，以提升召回。 |
| FR-3.10 | 系统应统计本体规模与**覆盖率**（已被条目标注过的知识点比例），并据此暴露知识库的内容缺口。 |

### 3.4 FR-4 内容管理与版本

> 溯源：任务书题目1「内容管理系统（CMS）：用于创建、编辑、发布和管理知识内容。支持多种
> 文件格式和多媒体内容。需提供指定天数/修改次数的版本管理。」

| 编号 | 需求描述 |
|---|---|
| FR-4.1 | 系统应为内容提供生命周期状态：`DRAFT`（草稿）、`PENDING`（待审）、`PUBLISHED`（已发布）、`ARCHIVED`（已归档）。 |
| FR-4.2 | 系统应支持状态流转：提交审核、发布、撤回发布、归档、恢复（恢复后回到草稿而非直接发布）。 |
| FR-4.3 | 系统应支持**按指定天数**自动建立版本快照：距上次快照达到 `interval_days` 天即建版。 |
| FR-4.4 | 系统应支持**按修改次数**自动建立版本快照：累计修改达到 `min_change_count` 次即建版。 |
| FR-4.5 | 系统应支持版本策略的三级作用域：`ITEM`（条目级）→ `CATEGORY`（分类级）→ `GLOBAL`（全局级），命中即停止。 |
| FR-4.6 | 系统应支持手工创建版本（需填写版本说明），以及发布、回滚时的**无条件**建版。 |
| FR-4.7 | 系统应支持版本差异比对，以行级 diff 展示新增 / 删除行，并展示标题、摘要、概念标注、标签的变化。 |
| FR-4.8 | 系统应支持版本回滚；回滚**不应删除**任何历史版本，而应生成一条 `ROLLBACK` 来源的新版本，并在回滚前为当前状态自动留存快照。 |
| FR-4.9 | 系统应提供版本数上限（`max_versions`），超出时淘汰最旧版本。 |
| FR-4.10 | 系统应能解释「当前为何该建 / 不该建版」，向用户给出判定依据（`snapshot-decision`）。 |

### 3.5 FR-5 系统管理

> 溯源：任务书综合考核要求（系统安全、可维护性）与「系统界面美观，使用友好」。

| 编号 | 需求描述 |
|---|---|
| FR-5.1 | 系统应支持用户登录、注册、查看当前用户信息与修改口令，登录后签发 JWT 令牌。 |
| FR-5.2 | 系统应支持管理员对用户进行增删改查与角色分配。 |
| FR-5.3 | 系统应记录关键操作的审计日志（操作类型、目标、操作人、IP、时间）。 |
| FR-5.4 | 系统应提供统计看板：知识总量、状态与类型分布、发布趋势、知识域分布、知识点热度。 |
| FR-5.5 | 系统应提供检索分析：总检索次数、平均耗时、热搜词、零结果词。 |
| FR-5.6 | 系统应提供向量索引状态查询与索引重建能力；重建应异步执行，不阻塞用户的保存操作。 |
| FR-5.7 | 系统应提供系统能力自检信息（当前向量模型、生成模型、是否处于降级状态）。 |
| FR-5.8 | 系统应提供 REST 接口文档（Swagger UI，路径 `/swagger-ui.html`）。 |

## 4 非功能性需求

| 编号 | 类别 | 需求描述 | 具体指标（取自配置） |
|---|---|---|---|
| NFR-1 | 性能 | 常规全文检索的响应时间应足够短，交互无感知卡顿 | 实测平均检索耗时约 **18 ms** 量级；配置 `search.max-page-size = 100` |
| NFR-2 | 性能 | 单次检索的关键词长度应受控，避免超长输入拖慢查询 | 关键词上限 120 字符（`SearchService.MAX_KEYWORD_LENGTH`） |
| NFR-3 | 性能 | 向量索引构建应可接受，且不阻塞用户操作 | 60 条知识条目 → 164 个分块，构建耗时约 **1.2 s**；索引异步重建 |
| NFR-4 | 性能 | 数据库连接池应能应对并发会话 | HikariCP：最小空闲 5、最大连接 20、连接超时 30 s |
| NFR-5 | 安全 | 认证应基于无状态令牌，令牌应有明确有效期 | JWT HS256，有效期 **720 分钟（12 小时）**，签发者 `njupt-kms` |
| NFR-6 | 安全 | 口令不得明文存储 | BCrypt 散列，`sys_user.password VARCHAR(128)` |
| NFR-7 | 安全 | 写操作应鉴权，公开只读接口可匿名访问 | 方法级 `@PreAuthorize`；`SecurityConfig` 中精确放行白名单 |
| NFR-8 | 安全 | 上传文件应受大小与类型限制 | 单文件上限 **300 MB**，单请求上限 **600 MB**，按媒体类型限定扩展名 |
| NFR-9 | 可用性 | 界面应美观、友好，关键操作路径短 | 关键操作三步内可达；所有列表页具备分页与空状态；危险操作二次确认 |
| NFR-10 | 可用性 | 检索无结果、问答无资料等情况应有明确引导 | 零结果建议、`weakMatch` 提示、RAG「资料未涵盖」说明 |
| NFR-11 | 可用性 | 图表信息应对色觉障碍用户与黑白打印保持可读 | 分类色板经色觉缺陷可辨识性校验；图表配「显示数据表」等价视图 |
| NFR-12 | 可维护性 | 前后端分离，模块边界清晰，核心算法有注释说明 | 后端 9 个业务模块，12 个控制器；关键算法有 javadoc 说明设计理由 |
| NFR-13 | 可维护性 | 系统应能在缺少外部依赖时降级运行 | 在线模型不可用时降级为本地哈希向量模型 / 离线抽取式回答 |
| NFR-14 | 可移植性 | 前端应能部署到任意静态服务器 | 采用 hash 路由，无需服务端 rewrite 配置 |
| NFR-15 | 一致性 | 冗余字段漂移应可修复 | 为分类计数、标签使用次数、条目纯文本提供重算入口 |

### 5.2 用例 UC-01：向知识库提问（RAG 问答）

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-01 |
| 名称 | 向知识库提问 |
| 主要参与者 | 浏览者（或编辑、管理员） |
| 前置条件 | 用户已登录；知识库已有内容；若需生成模型则已配置 API Key（否则走降级） |
| 触发条件 | 用户在「智能问答」页输入问题并点击「发送」 |

**主流程：**

| 步骤 | 参与者动作 | 系统响应 |
|---|---|---|
| 1 | 输入问题，如「需求分析和需求获取有什么区别？」 | 创建或复用问答会话，保存用户消息 |
| 2 | — | 实体链接识别问题中的知识点，沿本体关系扩展相邻概念，拼入检索串 |
| 3 | — | 混合检索：向量通道取 Top-20，关键字通道取 Top-20，RRF（k=60）融合 |
| 4 | — | 按条目去重组装上下文，加 `【来源 N】` 编号；调用生成模型 |
| 5 | — | 返回回答、引用列表、检索过程元数据并落库 |
| 6 | 查看回答，点击引用跳转原文，展开「检索过程」面板 | 展示命中知识点、扩展概念、各通道排名与融合得分 |

**备选流程：**

| 分支 | 条件 | 处理 |
|---|---|---|
| A1 | 生成模型未配置或调用失败 | 自动降级为**离线抽取式回答**，从检索片段中抽取最相关句子并按来源编号列出，界面明确标注降级 |
| A2 | 检索无相关分块 | 回答「知识库中暂时没有找到与该问题相关的内容」，并给出换词或查图谱的建议，不调用生成模型 |
| A3 | 在线向量模型调用失败 | 本次向量化降级为本地哈希向量模型，问答功能不中断 |
| A4 | 引用的条目已被归档 | 上下文组装阶段跳过归档条目 |

### 5.3 用例 UC-02：编辑知识条目并回滚版本

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-02 |
| 名称 | 编辑知识条目并回滚版本 |
| 主要参与者 | 编辑 |
| 前置条件 | 用户已登录且具备编辑权限；目标条目存在 |
| 触发条件 | 用户在「知识详情」页进入编辑并保存 |

**主流程：**

| 步骤 | 参与者动作 | 系统响应 |
|---|---|---|
| 1 | 修改正文并保存 | 累加条目的 `changeCount`，更新 `plain_text` 与关键词 |
| 2 | — | 由版本策略判定是否建版（天数阈值 **或** 修改次数阈值），满足则生成自动快照 |
| 3 | — | 发布事件 `ItemChangedEvent`，RAG 模块**异步**重建该条目的检索索引 |
| 4 | 打开「版本历史」页 | 展示版本列表、当前版本标记与版本策略判定说明 |
| 5 | 选择两个版本进行差异比对 | 以行级 diff 展示增删行（LCS 算法，折叠未改动上下文），并展示概念标注与标签的变化 |
| 6 | 选择历史版本并回滚 | 先为当前状态留存一份快照，再把目标版本内容写回条目，生成一条 `ROLLBACK` 来源的新版本 |

**备选流程：**

| 分支 | 条件 | 处理 |
|---|---|---|
| B1 | 正文与上一版本内容完全一致（MD5 相同） | 跳过自动建版（显式发布除外），不产生空版本 |
| B2 | 手动建版但正文未变化 | 提示「当前正文与最新版本完全一致，无需重复创建版本」 |
| B3 | 目标版本已是当前版本 | 提示「目标版本已是当前版本，无需回滚」 |
| B4 | 正文行数超过 3000 行 | diff 退化为「整体替换」标记，避免比对耗时过长 |
| B5 | 浏览者越权调用编辑接口 | 返回 `403` 无权限 |

### 5.4 用例 UC-03：全文检索与高级检索

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-03 |
| 名称 | 全文检索与高级检索 |
| 主要参与者 | 浏览者 |
| 前置条件 | 知识库已有已发布内容 |
| 触发条件 | 用户在检索入口输入关键词或在高级检索页设置条件 |

**主流程：**

| 步骤 | 参与者动作 | 系统响应 |
|---|---|---|
| 1 | 输入关键词「软件测试」 | 走 MySQL ngram 全文索引通道，**放大 6 倍**召回候选（上限 300 条） |
| 2 | — | 应用层重新打分：字段命中率×0.65 + 全文相关度×0.25 + 热度×0.10，标题完整命中额外 +0.20；本地分页 |
| 3 | — | 返回高亮标题、摘要片段、相关度得分与得分明细 |
| 4 | 切换排序为「最热」，或设置分类=技术报告、类型=REPORT、标签=答辩 | 条件通道按条件过滤并排序 |
| 5 | 输入不存在的词 | 返回空列表，并给出零结果建议（缩短关键词、单字改双字、相关知识点） |

**备选流程：**

| 分支 | 条件 | 处理 |
|---|---|---|
| C1 | 全文索引未命中或不可用 | 降级为模糊匹配（`LIKE`），保持有结果而不是白屏 |
| C2 | 结果仅为 ngram 二元组偶然重合（无标题/摘要命中） | 标记 `weakMatch=true`，界面提示「未找到精确匹配」，但**不隐藏**结果 |
| C3 | 关键词超长 | 截断至 120 字符 |
| C4 | 单字查询 | 因 `ngram_token_size = 2` 不命中，系统在无结果建议中提示改用双字及以上 |
