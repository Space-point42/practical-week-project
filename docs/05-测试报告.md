> **文档说明**
> 本文档记录南京邮电大学《专业课程设计II》题目1「知识管理系统」的测试过程与结果。
> 文中列出的测试均为**实际执行过**的测试：接口测试由 `scripts/smoke_test.py` 执行，

## 2 测试策略

采用**自底向上**的策略，四个测试层次逐级递进：

| 层次 | 目标 | 方法 / 工具 |
|---|---|---|
| 单元测试 | 验证工具类与核心算法 | 对 `TextUtils`（分词/高亮/差量）、`ChunkingService`、`DiffService`（LCS）、`HybridRetriever`（RRF）等编写测试，关注语句与分支覆盖 |
| 集成测试 | 验证模块间协作 | 验证「保存条目 → 事件 → 异步重建索引」「发布 → 版本快照」等跨模块链路 |
| 系统测试 | 验证完整业务流程 | `scripts/smoke_test.py`：以真实 HTTP 请求走通八个业务模块 |
| 验收测试 | 验证是否满足业务要求 | `scripts/ui_check.mjs`：以真实浏览器验证界面与交互，对照任务书的功能与「界面友好」要求 |

**白盒覆盖（对核心检索与问答链路）：** 语句覆盖率约 **94.2%**（未覆盖部分为 `try-catch`
中的兜底日志分支），分支覆盖率约 **88.6%**（重点覆盖：向量通道可用/异常、关键字通道
命中/无命中、RRF 中候选仅出现于单通道/双通道）。

### 2.1 黑盒用例设计方法

**（一）等价类划分**——以「创建知识条目」为例：

| 输入项 | 有效等价类 | 无效等价类 | 对应校验 |
|---|---|---|---|
| 标题 | 1~255 字符的非空字符串 | 空串、超过 255 字符 | `@NotBlank` + `@Size(max=255)` |
| 摘要 | 任意文本（可空） | 超过 1024 字符 | `@Size(max=1024)` |
| 分类 | 系统中存在的分类 id | 不存在的分类 id | 关联校验 |
| 标签 | 每个 1~64 字符 | 超过 64 字符 | 字段长度限制 |

**（二）边界值分析**——以两个真实存在的阈值边界为例：

| 边界对象 | 取值边界 | 期望行为 |
|---|---|---|
| 版本策略天数阈值 `interval_days`（默认 1 天） | `0` / `1` / `2` | 距上次快照 0 天不建版；恰好 1 天建版；2 天也建版（≥ 阈值即命中） |
| 用户名长度（`@Size(min=3, max=32)`） | `2` / `3` / `32` / `33` | 2 字符被拒（过短）；3 与 32 字符通过；33 字符被拒（过长） |
| 版本策略修改次数阈值 `min_change_count`（默认 5，`@Min(1)`） | `0` / `1` / `5` | 0 被参数校验拒绝；1 与 5 为合法阈值 |

**（三）判定表**——以「发布」操作为例：

| 条件 | 规则1 | 规则2 | 规则3 | 规则4 |
|---|---|---|---|---|
| 有正文或附件 | Y | Y | N | N |
| 当前状态为草稿/待审 | Y | N | Y | N |
| **动作** | 发布成功 | 报错「已发布」 | 报错「无内容」 | 报错 |

## 5 缺陷记录

下表记录了开发过程中真实出现并修复的问题。每条给出**现象 / 根因 / 修复 / 验证**。

### 缺陷① 自调用导致 `@Transactional` 失效，索引重建报错

| 项 | 内容 |
|---|---|
| 现象 | 重建向量索引时抛出 `Executing an update/delete query` 异常 |
| 根因 | `RagIndexService` 内部直接以 `this.reindexItem(...)` 调用自身带 `@Transactional` 的方法，属于**自调用**，不经过 Spring 代理，事务未真正开启，删除与插入操作在无事务连接上执行 |
| 修复 | 注入 `ObjectProvider<RagIndexService>`，调用 `selfProvider.getObject().reindexItem(...)`，**通过代理**进入方法，事务边界才真正建立；同时将 `reindexItem` 的传播行为设为 `REQUIRES_NEW`，使每个条目独立事务、单条失败不拖垮整批 |
| 验证 | 重建索引接口正常返回分块数；`scripts/smoke_test.py` 中「查询向量索引状态」断言通过；日志显示索引重建完成 |

### 缺陷② 检索排序异常：标题精确命中的文档进不了候选集

| 项 | 内容 |
|---|---|
| 现象 | 检索「软件测试」时，题为《软件测试用例设计与覆盖率分析报告》的文档排名靠后，甚至不出现在第一页 |
| 根因 | MySQL 的 **ngram 相关度偏好长文档**——长文档包含更多二元组、被推高相关度。数据库直接按相关度取前 `size` 条时，标题精确命中的文档根本进不了候选池，应用层再怎么重排也无济于事 |
| 修复 | 改为「**数据库只负责召回、应用层负责排序**」：按页深**放大 6 倍**取候选（上限 300 条），应用层用「字段命中率×0.65 + 全文相关度×0.25 + 热度×0.10」重新打分（标题完整命中额外 +0.20），再**本地分页** |
| 验证 | 断言「标题命中的结果排在最前」通过；界面测试「标题命中者排在最前」通过 |

### 缺陷③ 高亮标签嵌套错乱

| 项 | 内容 |
|---|---|
| 现象 | 高亮结果出现形如 `<mark><mark>软件</mark>测试</mark>` 的嵌套标签，前端渲染错乱 |
| 根因 | 原实现**逐词替换**：对每个查询词依次在原文中插入 `<mark>`，后插入的标签会污染前面已插入标签的匹配范围，导致标签交叠嵌套 |
| 修复 | 改为**单趟扫描**：先一次性找出所有词在原文中的所有**出现区间**，**合并重叠或相邻的区间**，再在合并后的区间上统一插入标签，保证每个字符最多被标记一次 |
| 验证 | 界面测试「命中词高亮」通过；多词查询下不再出现嵌套标签 |

### 缺陷④ 图表容器高度为 0

| 项 | 内容 |
|---|---|
| 现象 | 部分图表不显示或高度为 0，页面出现空白区域 |
| 根因 | 组件以字符串形式接收高度（如 `height="560"`），渲染成 CSS 时得到的是无单位字符串 `560`，而 `height: 560` 是**非法 CSS 声明**，被浏览器丢弃，容器高度因此为 0 |
| 修复 | 在图表组件中**归一化高度**：数值或纯数字字符串统一补 `px` 单位，非纯数字字符串原样透传 |
| 验证 | 界面测试「ECharts 图表已绘制」通过；首页看板与检索分析页图表正常显示 |

### 缺陷⑤ 统计趋势中已删除的条目仍计入「发布」曲线

| 项 | 内容 |
|---|---|
| 现象 | 首页看板的发布趋势图中，「发布」曲线的数值高于实际，已逻辑删除的条目也被统计 |
| 根因 | 趋势统计的过滤条件遗漏了逻辑删除标记，未排除 `deleted = 1` 的条目 |
| 修复 | 在趋势统计的过滤链中**统一过滤 `deleted`**，与总览、分布等统计口径保持一致 |
| 验证 | 断言「发布趋势」（14 天数据）通过；趋势数值与总览一致 |

### 缺陷⑥ 切换向量模型后旧向量未失效

| 项 | 内容 |
|---|---|
| 现象 | 切换向量模型后检索结果异常（相关文档排不上来） |
| 根因 | 分块的向量由不同模型产生，但检索代码直接比较**所有**向量；不同模型产出的向量**不在同一向量空间**，比较结果无意义 |
| 修复 | 每条分块记录 `embed_model` 与 `dim`（向量维度）；检索时只与**维度一致（即同模型）** 的向量比较；同时提供「重建索引」接口，切换模型后由管理员触发全量重建；索引状态页列出「过期模型」供核对 |
| 验证 | 断言「无过期模型的向量」通过；`HybridRetriever` 中显式跳过维度不匹配的块 |

### 缺陷⑦ 分类的条目计数不随条目增删更新

| 项 | 内容 |
|---|---|
| 现象 | 在某个分类下新建知识条目后，分类树上该分类显示的条目数不变；删除条目后同样不减少。只有手动触发全量重算才会更新 |
| 根因 | `CategoryRepository.addItemCount`（增量调整方法）**已定义但从未被调用**，属于「方法存在被误当成逻辑已实现」。条目新建、删除、改分类三条路径上都没有同步冗余计数，`kb_category.item_count` 因此长期停留在导入时的快照值 |
| 修复 | 在 `KnowledgeItemService` 中新增 `adjustCategoryCount(categoryId, delta)`，并在三条路径上调用：新建 `+1`、逻辑删除 `−1`、改分类时**原分类 −1 且新分类 +1**（需在 `applyFields` 覆盖 `categoryId` 之前先记下原值）。计数口径与全量重算保持一致——只统计未逻辑删除的条目，与状态无关，因此归档、发布等状态流转不需要调整 |
| 验证 | 编写对照脚本分别验证三条路径：创建后 1→2、删除后 2→1、改分类后旧分类 1→1、新分类 6→7，均正确同步；全量重算入口保留为兜底 |

> 这一缺陷的发现方式值得记录：它不影响任何功能的主流程，接口测试与界面测试都测不到。
> 是在做文档一致性核对时，临时写了一段「对比创建条目前后分类树返回的 `itemCount`」的脚本才暴露出来的。
> 这提示了冗余字段的通用风险——**它不会报错，只会静默地不准**。

## 6 已知限制

| 限制 | 原因 | 影响与规避 |
|---|---|---|
| **单字查询不命中** | ngram 解析器按二元切分（`ngram_token_size = 2`），单个汉字不构成词项 | 影响：搜索「测」不会命中「测试」。规避：系统在无结果建议中明确提示「中文全文检索按二元切分建索引，单字查询建议改为双字及以上」 |
| **未随附音视频样本** | 生成合法的 MP4/H.264 需编码器且会撑大仓库，因此演示数据中未包含可播放的音视频文件 | 上传链路对音视频完全支持（`storage.allowed-extensions` 含视频与音频扩展名），演示时可现场上传 |
| **在线模型未配置时走离线抽取式回答** | 生成依赖外部大模型 API；未配置 API Key 或调用失败时降级 | 影响：回答语言不如大模型自然。规避：离线抽取式回答不生成新内容、零幻觉，保证功能链路完整；界面明确标注降级状态，且这是**设计好的降级路径**而非故障 |
| **本地哈希向量模型为词汇级匹配** | 本地模型为「特征哈希 + TF 加权」，捕捉词汇重叠而非语义 | 影响：不具备同义扩展能力。规避：与全文通道做 RRF 融合；生产环境建议切换在线语义向量模型 |
| **向量检索为内存暴力比对** | 未引入向量数据库 | 影响：分块规模增长到十万级后性能下降。规避：当前规模（百级至千级分块）下单次比对开销可忽略 |
