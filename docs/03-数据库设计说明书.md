# 知识管理系统 数据库设计说明书

> **文档说明**
> 本文档描述南京邮电大学《专业课程设计II》题目1「知识管理系统」的数据库设计，按
> 《数据库原理》课程要求的三阶段方法组织：**概念结构设计 → 逻辑结构设计 → 物理结构设计**，
> 并在其间给出范式判定与反规范化权衡。文中所有表名、字段名、约束与索引均取自实际建库脚本
> `backend/src/main/resources/db/schema.sql`，共 **20 张表**，可逐条对照核对。
> 概念模型见 `docs/screenshots/` 中随附的 E-R 图（同时作为演示附件挂载于
> 「数据库逻辑结构设计与规范化分析」条目上）。

## 1 设计过程

数据库设计遵循「需求 → 概念模型 → 逻辑模型 → 物理模型」的递进路径，每一步都以上一步的
输出为输入，并接受规范化与性能的双重检验：

| 阶段 | 输入 | 输出 | 主要方法 | 本文对应章节 |
|---|---|---|---|---|
| 需求分析 | 需求规格说明书 | 数据项与处理需求清单 | 从需求文字抽取名词作候选实体 | 第 2 章 |
| 概念结构设计 | 数据项清单 | E-R 图（实体、联系、基数） | 自底向上（局部 E-R → 集成） | 第 2 章 |
| 逻辑结构设计 | E-R 图 | 关系模式集合 | E-R 转关系模式规则 + 规范化 | 第 3、4 章 |
| 物理结构设计 | 关系模式 | 表、索引、存储结构 | 索引选择、数据类型与存储布局 | 第 6、7 章 |
| 完整性设计 | 关系模式 | 主键、外键、删除策略 | 参照完整性 + 应用层约束 | 第 5 章 |

**从需求到实体的抽取示例：** 对「知识库、搜索引擎、本体、CMS、系统管理」五类需求逐句
分析，抽取名词作为候选实体——用户、角色、知识条目、附件、分类、标签、本体概念、本体关系、
版本、策略、会话、消息、检索日志、审计日志——再判别哪些名词实为**联系**（如「标注」
「标签关联」），从而避免把联系误建为实体。

## 2 概念结构设计

### 2.1 实体集

| 实体 | 主要属性 | 说明 |
|---|---|---|
| 用户 | 登录名、口令散列、姓名、邮箱、单位、状态 | 系统使用者 |
| 角色 | 编码、名称、描述 | 管理员 / 编辑 / 浏览者 |
| 知识条目 | 标题、摘要、正文、纯文本、资产类型、状态、版本号、计数 | 知识资产主实体 |
| 附件 | 文件名、存储名、路径、大小、媒体类型、抽取正文 | 条目的多格式素材 |
| 分类 | 名称、编码、父分类、层级、路径、条目计数 | 知识的管理视角层次结构 |
| 标签 | 名称、颜色、使用次数 | 内容的交叉特征 |
| 本体概念 | 编码、名称、英文名、别名、父概念、层级、路径、知识域、难度、重要度 | 知识点 |
| 本体关系类型 | 编码、名称、逆关系、是否有向、描述 | 关系字典 |
| 本体关系 | 源概念、目标概念、关系类型、权重、说明 | 语义三元组 |
| 历史版本 | 版本号、标题、正文快照、概念/标签快照、变更说明、来源、内容哈希 | 版本快照 |
| 版本策略 | 作用域、作用对象、天数阈值、次数阈值、版本上限 | 建版规则 |
| 检索分块 | 条目、来源类型、块序号、文本、向量、维度、向量模型 | RAG 索引单元 |
| 问答会话 | 用户、标题 | 会话 |
| 问答消息 | 会话、角色、内容、引用、检索元数据、模型、耗时 | 一问一答 |
| 检索日志 | 用户、关键词、检索类型、结果数、耗时 | 检索行为记录 |
| 审计日志 | 用户、操作、目标类型、目标、明细、IP | 操作留痕 |

### 2.2 联系及基数

| 联系 | 两端实体 | 基数 | 转换后的落点 |
|---|---|---|---|
| 拥有 | 用户 — 角色 | **M:N** | 关联表 `sys_user_role` |
| 创建 | 用户 — 知识条目 | 1:N | `kb_item.author_id` 外码 |
| 归类 | 分类 — 知识条目 | 1:N | `kb_item.category_id` 外码 |
| 子分类 | 分类 — 分类 | 1:N（自反） | `kb_category.parent_id` 自引用 |
| 打标签 | 知识条目 — 标签 | **M:N** | 关联表 `kb_item_tag` |
| 标注 | 知识条目 — 本体概念 | **M:N（带联系属性）** | 关联表 `kb_item_concept`，含 `source`、`confidence` |
| 上传 | 知识条目 — 附件 | 1:N | `kb_attachment.item_id` 外码 |
| 父概念 | 本体概念 — 本体概念 | 1:N（自反） | `ont_concept.parent_id` 自引用 |
| 关系三元组 | 本体概念 — 本体概念 | **M:N（带关系类型）** | `ont_relation`，主码含关系类型 |
| 版本快照 | 知识条目 — 历史版本 | 1:N | `cms_item_version.item_id` 外码 |
| 适用策略 | 版本策略 — 分类/条目 | 1:N（多态） | `cms_version_policy.scope + scope_id` |
| 分块 | 知识条目 — 检索分块 | 1:N | `rag_chunk.item_id` 外码 |
| 会话消息 | 问答会话 — 问答消息 | 1:N | `rag_message.session_id` 外码 |

> **E-R 图：** 上述实体与联系构成完整的 E-R 图，见 `docs/screenshots/` 目录随附的
> 「知识管理系统-E-R图.png」（生成于演示数据初始化时，同时作为附件挂载在条目
> 《数据库逻辑结构设计与规范化分析》上）。

### 2.3 关键转换规则应用

| 规则 | 应用 | 说明 |
|---|---|---|
| 实体 → 关系模式 | 每个实体建一张表 | 实体属性即表属性，标识即主键 |
| 1:N 联系 | 1 端主码放入 N 端作外码 | 如「分类—条目」把 `category_id` 放入 `kb_item` |
| M:N 联系 | 单独建关联表，码为两端主码组合 | 如 `kb_item_tag(item_id, tag_id)` |
| 带属性的 M:N | 联系属性放入关联表 | `kb_item_concept(item_id, concept_id, source, confidence)` |
| 自反 1:N | 自引用外码 + 物化路径 | `kb_category.parent_id` 与 `path` |
| 多态联系 | 作用域字段区分 | `cms_version_policy.scope + scope_id` |

## 3 逻辑结构设计

数据库共 **20 张表**，按功能分为 7 组。以下逐组列出表名、中文名、主键与关键字段。

### 3.1 用户与权限（3 张）

#### `sys_user` — 系统用户

| 主键 | 说明 |
|---|---|
| `id` | 自增主键 |

| 关键字段 | 类型 | 说明 |
|---|---|---|
| `username` | `VARCHAR(64)` | 登录名，`UNIQUE` |
| `password` | `VARCHAR(128)` | BCrypt 口令散列 |
| `real_name` / `email` / `avatar` / `department` | 变长 | 姓名、邮箱、头像、单位/班级 |
| `status` | `TINYINT` | 1=启用 0=停用 |
| `last_login_at` | `DATETIME` | 最近登录时间 |

#### `sys_role` — 角色

| 主键 | 说明 |
|---|---|
| `id` | 自增主键 |

| 关键字段 | 类型 | 说明 |
|---|---|---|
| `code` | `VARCHAR(32)` | 角色编码 `ADMIN` / `EDITOR` / `VIEWER`，`UNIQUE` |
| `name` / `description` / `sort_order` | — | 名称、描述、排序 |

#### `sys_user_role` — 用户-角色关联

| 主键 | 说明 |
|---|---|
| `(user_id, role_id)` | 复合主键 |

| 关键字段 | 说明 |
|---|---|
| `user_id` → `sys_user(id)` | `ON DELETE CASCADE` |
| `role_id` → `sys_role(id)` | `ON DELETE CASCADE`；`idx_ur_role` 支持按角色反查 |

### 3.2 系统配置（1 张）

#### `sys_setting` — 系统配置项

| 主键 | 说明 |
|---|---|
| `id` | 自增主键 |

| 关键字段 | 类型 | 说明 |
|---|---|---|
| `cfg_key` | `VARCHAR(64)` | 配置键，`UNIQUE` |
| `cfg_value` | `VARCHAR(512)` | 配置值 |
| `cfg_group` | `VARCHAR(32)` | 配置分组，默认 `common` |
| `description` | `VARCHAR(255)` | 说明 |

> 用于存放运行期可改的配置（如版本策略、RAG 参数），与配置文件中的默认值配合使用。

### 3.3 知识本体（3 张）

#### `ont_concept` — 本体概念（知识点）

| 主键 | 说明 |
|---|---|
| `id` | 自增主键 |

| 关键字段 | 类型 | 说明 |
|---|---|---|
| `code` | `VARCHAR(64)` | 概念唯一编码，如 `SE.REQ.ELICITATION`，`UNIQUE` |
| `name` / `en_name` | `VARCHAR` | 中文名、英文名 |
| `aliases` | `VARCHAR(512)` | 别名，逗号分隔，**用于实体链接** |
| `parent_id` | `BIGINT` | 父概念，自引用 |
| `level` / `path` | `TINYINT` / `VARCHAR(512)` | 层次深度、物化路径（如 `/1/5/12/`） |
| `domain` | `VARCHAR(64)` | 知识域（软件工程/数据库/知识管理） |
| `difficulty` / `importance` | `TINYINT` | 认知难度、重要程度（1~5） |
| `color` / `builtin` / `sort_order` | — | 图谱配色、内置标记、排序 |

#### `ont_relation_type` — 本体关系类型

| 主键 | 说明 |
|---|---|
| `id` | 自增主键 |

| 关键字段 | 类型 | 说明 |
|---|---|---|
| `code` | `VARCHAR(32)` | 关系编码，`UNIQUE` |
| `name` | `VARCHAR(64)` | 关系名称 |
| `inverse_code` | `VARCHAR(32)` | 逆关系编码，对称关系与自身相同 |
| `directed` | `TINYINT` | 1=有向 0=无向（对称） |
| `color` / `description` | — | 图谱配色、语义说明 |

#### `ont_relation` — 本体关系（三元组）

| 主键 | 说明 |
|---|---|
| `id` | 自增主键 |

| 关键字段 | 类型 | 说明 |
|---|---|---|
| `source_id` / `target_id` | `BIGINT` | 源、目标概念，外键指向 `ont_concept.id` |
| `relation_type` | `VARCHAR(32)` | 关系类型编码（引用 `ont_relation_type.code`） |
| `weight` | `DECIMAL(4,2)` | 关系强度 0~1 |
| `description` | `VARCHAR(512)` | 三元组断言的自然语言表述 |
| **唯一键** | `(source_id, target_id, relation_type)` | 防止重复三元组 |

## 4 规范化分析

### 4.1 主键与函数依赖检查

| 关系模式 | 码 | 函数依赖要点 | 满足范式 |
|---|---|---|---|
| `kb_item_tag(item_id, tag_id)` | `(item_id, tag_id)` | 两属性均为主属性，无非主属性对码的部分/传递依赖 | **3NF，且 BCNF** |
| `kb_item_concept(item_id, concept_id, source, confidence)` | `(item_id, concept_id)` | `source`、`confidence` 完全依赖于整个码（描述「某条目标注某概念」这一联系） | **3NF，且 BCNF** |
| `ont_relation(source_id, target_id, relation_type, weight, description)` | `(source_id, target_id, relation_type)` | 三个码属性均为主属性，`weight`/`description` 完全依赖码 | **3NF，且 BCNF** |
| `kb_item(id, title, ..., category_id, ...)` | `id` | 各非主属性直接依赖 `id`；分类名称不在本表，**不存在传递依赖** | **3NF** |
| `kb_category(id, name, ..., parent_id, path, item_count)` | `id` | `path` 由祖先链决定、`item_count` 为派生计数，见下 | 主体 **3NF**（含 2 处有意冗余） |
| `sys_user_role(user_id, role_id)` | `(user_id, role_id)` | 全主属性关联表 | **3NF，且 BCNF** |
| `cms_item_version(id, item_id, version_no, ...)` | `id`（另有 `item_id, version_no` 唯一） | 版本属性完全依赖版本标识 | **3NF** |
| `rag_chunk(id, item_id, chunk_index, content, embedding, dim, embed_model)` | `id` | `dim`、`embed_model` 描述该行的向量，属**该行自身**属性而非传递依赖 | **3NF** |

**典型反例说明（用于对比）：** 若把「分类名称」冗余进 `kb_item`，则存在
`id → category_id → category_name` 的传递依赖，只能满足 2NF，并会带来更新异常
（分类改名需批量更新所有条目）。本系统**未**这样做，故 `kb_item` 满足 3NF。

### 4.2 有意的反规范化及其一致性维护

规范化避免**意外的**更新异常，但不禁止**有意的**冗余。本系统刻意在 3 处引入冗余，
以加快读路径，并为每处提供重算入口以保证一致性：

| 冗余字段 | 位置 | 动机 | 一致性保障 |
|---|---|---|---|
| `item_count` | `kb_category` | 分类树每级都需显示条目数，实时 `COUNT` 代价高 | 服务层在条目增删改时增减；初始化导入结束后统一重算；提供重算入口 |
| `use_count` | `kb_tag` | 标签云按热度排序，避免每次分组统计 | 条目保存后统一重算（`DemoContentSeeder.recalculateTagUsage`） |
| `plain_text` | `kb_item` | 检索与向量化需要去标记后的正文，避免每次查询时转换 | 保存时由 Markdown 转换生成；版本快照另存概念/标签快照 |

**权衡结论：** 反规范化的收益是**读路径变快**，代价是**写路径需保证冗余字段一致**。
本系统为每个冗余字段都提供了重算能力，即便出现漂移也能一键修复，把「一致性风险」转为
「可修复的、有界的工程问题」。此外，`rag_chunk.item_title` 也保存了一份冗余标题，
目的是让历史引用在条目改名后仍能还原当时的标题。

## 5 完整性约束与删除策略

### 5.1 实体完整性

所有主表均以自增 `id` 或复合主键保证实体完整性；`ont_concept.code`、`kb_item_tag` 等
关键编码设有 `UNIQUE` 唯一约束。

### 5.2 参照完整性与外键删除策略

数据库层通过外键约束维护参照完整性，删除策略按「子数据是否脱离父数据即无意义」来选择：

| 外键 | 子表 → 父表 | 删除策略 | 理由 |
|---|---|---|---|
| `fk_item_category` | `kb_item` → `kb_category` | **SET NULL** | 分类删除时条目仍有价值，仅暂未归类 |
| `fk_it_item` | `kb_item_tag` → `kb_item` | **CASCADE** | 条目删除后标签关联无意义 |
| `fk_it_tag` | `kb_item_tag` → `kb_tag` | **CASCADE** | 标签删除后关联无意义 |
| `fk_ic_item` | `kb_item_concept` → `kb_item` | **CASCADE** | 同上 |
| `fk_ic_concept` | `kb_item_concept` → `ont_concept` | **CASCADE** | 概念删除后标注无意义 |
| `fk_att_item` | `kb_attachment` → `kb_item` | **CASCADE** | 附件隶属条目 |
| `fk_rel_source` / `fk_rel_target` | `ont_relation` → `ont_concept` | **CASCADE** | 概念删除后其关系无意义 |
| `fk_ur_user` / `fk_ur_role` | `sys_user_role` → `sys_user` / `sys_role` | **CASCADE** | 关联随任一端消失 |
| `fk_version_item` | `cms_item_version` → `kb_item` | **CASCADE** | 版本快照隶属条目 |
| `fk_chunk_item` | `rag_chunk` → `kb_item` | **CASCADE** | 分块是条目的派生数据 |
| `fk_msg_session` | `rag_message` → `rag_session` | **CASCADE** | 消息隶属会话 |

**关于 RESTRICT（受限删除）：** 本库并未在数据库层使用 `RESTRICT`；对「不应被级联删除」
的对象，系统在**服务层**实施等价于 RESTRICT 的保护，并给出可操作的错误信息：

| 对象 | 保护规则 | 错误提示 |
|---|---|---|
| 内置知识点（`builtin = 1`） | 禁止删除 | 「系统内置知识点不允许删除」 |
| 含子知识点的概念 | 禁止删除 | 「该知识点下仍有 N 个子知识点，请先删除或迁移子节点」 |
| 被条目标注的概念 | 禁止删除 | 「该知识点已被 N 条知识条目引用，请先解除标注」 |
| 含子分类的分类 | 禁止删除 | 「该分类下仍有子分类，无法删除」 |
| 最后一条全局策略 | 禁止删除 | 「必须保留至少一条全局策略」 |

选择此策略的原因：数据库层的 `RESTRICT` 只能给出通用的外键冲突错误，而业务层能给出
**「为什么不能删、应该先做什么」**的可操作提示，更符合「界面友好」的非功能需求。

### 5.3 用户定义完整性

| 约束 | 位置 | 规则 |
|---|---|---|
| 状态枚举 | `kb_item.status` | `DRAFT`/`PENDING`/`PUBLISHED`/`ARCHIVED` |
| 资产类型枚举 | `kb_item.asset_type` | 八类取值 |
| 策略作用域 | `cms_version_policy.scope` | `GLOBAL`/`CATEGORY`/`ITEM`，非全局必须指定 `scope_id` |
| 阈值下界 | `cms_version_policy` | `interval_days ≥ 0`、`min_change_count ≥ 1`、`max_versions ≥ 1` |
| 标题/摘要长度 | `kb_item` | 标题 ≤ 255、摘要 ≤ 1024（应用层校验） |
| 用户名长度 | `sys_user` | 3~32 字符（应用层校验） |

## 7 物理结构设计

### 7.1 字符集与排序规则

- 数据库、库中所有表统一使用 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`，支持完整 Unicode
  （含 emoji，因此 `kb_item.content` 可安全存放各类符号）。
- 连接串显式设置 `characterEncoding=UTF-8`，由 Connector/J 8 自动协商为服务端 `utf8mb4`。
- 全文索引使用 **ngram 解析器**，`ngram_token_size = 2`，即中文按**二元切分**建索引；
  这是「单字查询不命中」的根因，也是一项已知限制。

### 7.2 数据类型选择

| 场景 | 采用类型 | 理由 |
|---|---|---|
| 正文 / 纯文本 / 会话内容 | `LONGTEXT` | 正文可能较长，需容纳数万字 |
| 块文本 / 引用 / 检索元数据 | `TEXT` | 规模有限，`TEXT` 足够 |
| 向量 | `MEDIUMBLOB` | 以 `float32` 小端序列存储；512 维占 2048 字节，`MEDIUMBLOB`（16 MB 上限）余量充足 |
| 关系强度 / 置信度 | `DECIMAL(4,2)` | 精确的小数字段，避免浮点误差 |
| 布尔语义字段 | `TINYINT` | `status`、`builtin`、`auto_snapshot`、`enabled`、`deleted` |
| 枚举语义字段 | `VARCHAR` | `status`、`asset_type`、`scope` 等，可读性优于整型编码 |
| 时间戳 | `DATETIME` | 统一 `Asia/Shanghai` 时区；`created_at`/`updated_at` 有默认值与自动更新 |
| 内容哈希 | `CHAR(32)` | MD5 定长 |

### 7.3 向量的物理表示

向量以 **`float32` 小端字节序列**存入 `rag_chunk.embedding`（`MEDIUMBLOB`），并同行记录
`dim`（维度）与 `embed_model`（模型标识）。转换与相似度计算由 `EmbeddingService` 提供
（`toBytes` / `fromBytes` / `cosine`）。由于向量已做 L2 归一化，余弦相似度等于点积，
省去一次开方。

> **重要约束：** 不同模型产出的向量**不在同一向量空间**，直接比较无意义。因此检索时只与
> 维度一致（即同一模型产生）的向量比对；切换向量模型后必须重建索引，`embed_model` 与
> `dim` 正是支撑这一判断的元数据。

### 7.4 层次结构的物理支持

分类树与概念树均采用 **「邻接表 + 物化路径」** 双表示：

- `parent_id` 表达直接的父子关系，便于维护与单层查询；
- `path`（形如 `/1/5/12/`）保存从根到当前节点的完整路径，使**子树查询**可以使用
  `path LIKE '/1/5/%'` 一次完成，避免递归查询（CTE）带来的复杂度与性能开销。

该设计是「以空间换查询效率」的典型应用：路径字段占用少量存储，换取子树检索的常数级索引命中。

### 7.5 文件存储的物理布局

附件文件不存入数据库，而是存储在文件系统中，数据库仅保留元数据：

| 项 | 设计 |
|---|---|
| 存储根目录 | `kms.storage.root`，默认 `../storage` |
| 目录布局 | `<root>/yyyy/MM/<uuid>.<ext>`，**按年月分目录**，避免单目录文件过多 |
| 文件名 | UUID 命名，防冲突与信息泄露；原始文件名保留在 `kb_attachment.file_name` |
| 扩展名白名单 | 按媒体类型分组（文档 / 图片 / 视频 / 音频），见 `kms.storage.allowed-extensions` |
| 大小限制 | 单文件 300 MB，单请求 600 MB，内存阈值 2 MB |

数据库与文件系统的引用一致性通过外键 `fk_att_item`（`ON DELETE CASCADE`）与
`file_path` 相对路径共同维护。

### 7.6 表选项

所有表使用 `ENGINE = InnoDB`（事务、行锁、外键支持），字符集 `utf8mb4`，并为每张表
添加了中文 `COMMENT` 说明，便于查阅与维护。建库脚本可重复执行（`DROP TABLE IF EXISTS`），
用于初始化开发与演示环境。
