## 1 小组分工

小组共 6 人，按**功能域**分工。常见的"一人前端、一人数据库、其余后端"这类按技术层次的
划分有两个问题：每个人只接触系统的一个切面，被问到业务细节时答不上来；
模块边界与人的边界不一致，出问题时难以定位责任人。
因此本组按功能域划分，每人完整负责一个功能域的**数据库设计、后端实现、前端页面、
测试用例与文档**，即"从表结构到界面"的纵向全栈。

| 成员 | 姓名 | 负责功能域 | 主要交付物 |
|---|---|---|---|
| 1 | 【姓名】 | **需求分析与数据库设计**（含权限与统计看板） | 需求规格、E-R 图、20 张表建表脚本、规范化分析、登录页与首页看板 |
| 2 | 【姓名】 | **知识库与内容组织** | 知识条目 CRUD、分类树、标签、状态流转、知识库列表页与详情页 |
| 3 | 【姓名】 | **内容编辑、多媒体附件与归档审计** | 多格式正文抽取、文件存储、附件预览、归档、审计日志、编辑器页 |
| 4 | 【姓名】 | **知识本体与知识图谱** | 107 个知识点、7 种语义关系、图谱可视化、推理、实体链接 |
| 5 | 【姓名】 | **搜索引擎与版本管理** | ngram 全文检索、高级检索、应用层重排序、双阈值版本策略、LCS 差异比对 |
| 6 | 【姓名】 | **检索增强问答（RAG）** | 文本分块、向量化、混合检索与 RRF 融合、生成与引用溯源、问答页 |

六人工作量在 3,400–4,600 行代码之间（±18%）。完全均等不现实——
知识库与 RAG 两个模块的业务复杂度天然更高，小组通过把文档撰写与测试数据准备
多分配给代码量较少的成员来拉平总工作量。**每个人的详细分工、关键代码位置、
必须掌握的知识点与答辩预设问答见 [`docs/分工与答辩要点/`](分工与答辩要点/00-分工总览.md)。**

**协作方式：** 代码用 Git 管理（主干开发 + 特性分支），文档与代码同仓；每日站会同步阻塞项；
关键算法（分块、RRF、LCS diff、高亮）由作者自测，再由负责检索与版本管理的成员复核。

## 3 项目管理实践

### 3.1 进度管理

- 采用**两周一迭代**的计划表，任务拆到「半天到一天」颗粒度，避免任务过于笼统而无法跟踪；
- 每日站会同步三件事：昨天完成什么、今天计划什么、有什么阻塞；
- 里程碑：第 7 周末「可启动的后端」、第 8 周周三「界面可用」、第 8 周周四「测试报告」；
- 对关键路径上的任务（本体建模、RAG 流水线）预留缓冲，避免其延迟传导到整体验收。

### 3.2 风险管理

第 7 周识别出 5 项风险，其中最关键的一项是「**外部大模型 API 不可用**」。

| 风险 | 影响 | 应对策略 | 结果 |
|---|---|---|---|
| **外部大模型 API 不可用** | 答辩现场网络不通或未配置 Key 时，问答功能完全无法演示 | 设计**降级路径**：检测不到 API Key 或调用失败时，自动切换为「离线抽取式回答」（从检索片段中抽取最相关句子、按来源编号列出），不生成新内容、零幻觉 | 已消除，问答在任何环境均可演示 |
| 向量模型不可用 | 向量通道失效 | 自动降级为本地哈希向量模型，问答不中断 | 已消除 |
| ngram 单字查询不命中 | 部分查询无结果 | 界面明确提示「单字改双字」 | 已缓解（记为已知限制） |
| 图谱节点过多导致渲染慢 | 演示卡顿 | 提供「按知识域筛选」缩小范围 | 已缓解 |
| 两人并行开发同一模块产生冲突 | 返工 | 提前划分模块边界，接口先冻结 | 已避免 |

其中「外部大模型 API 不可用」的应对决策被写入架构文档，作为「考虑环境约束、体现设计
鲁棒性」的加分点：**降级不是故障，而是设计的一部分**。

### 3.3 配置管理

- **代码管理：** Git，分支策略为主干开发 + 特性分支，提交信息描述「改了什么、为什么」；
- **数据库脚本可重复执行：** `db/schema.sql` 使用 `DROP TABLE IF EXISTS`，任何环境都能一键重建；
- **演示数据可控：** 首次启动在表为空时自动导入本体与演示数据，保证演示环境一致；
- **文档与代码同仓：** 设计文档随代码变更同步更新，避免文档与实现脱节。

### 3.4 质量保证

- 提交前代码评审，关键算法（分块、RRF、LCS diff、高亮）要求有单元测试；
- 核心检索与问答链路的语句覆盖率约 94.2%、分支覆盖率约 88.6%；
- 两个自动化测试脚本可随时运行，用于**答辩前的环境自检**，避免演示时才发现某模块不可用；
- 缺陷统一记录、跟踪到验证通过为止（见第 4 节与《测试报告》第 5 节）。

## 4 遇到的问题与解决（经验教训）

以下是开发过程中真实遇到的问题。相比「如何修好」，更值得记录的是**从中学到了什么**。

### 4.1 派生数据必须记录它是怎么产生的

**问题：** 切换向量模型后，旧向量未失效，检索结果异常。
**原因：** 分块的向量由不同模型产生，但检索代码直接比较所有向量；不同模型的向量空间不同，
比较结果无意义。
**解决：** 每条分块记录 `embed_model` 与 `dim`，检索时只与同模型向量比较，并提供重建索引接口。

**经验教训：** 凡是**派生数据**（向量、缓存、计数、索引），都必须记录它是**由什么、在什么
条件下**产生的（模型标识、维度、算法版本、时间戳），否则日后无法判断它是否仍然有效。
这条经验后来被推广到整个项目——例如版本快照同时保存「概念名」而非只保存 id，就是为了让
历史记录在概念被重命名后仍能自解释。

### 4.2 框架能力有边界，要理解它「为什么」生效

**问题：** 索引重建时抛 `Executing an update/delete query`。
**原因：** 类内自调用 `this.reindexItem(...)` 不经过 Spring 代理，`@Transactional` 未生效。
**解决：** 通过 `ObjectProvider` 取自身代理再调用。

**经验教训：** 声明式注解（`@Transactional`、`@Async`、`@PreAuthorize`）依赖**代理**机制，
自调用会绕过代理。这不是「配置问题」，而是对框架底层机制理解不足。此后凡是「在同一类中调用
本类带注解方法」的地方都要多问一句：这次真的过代理了吗？

### 4.3 数据库擅长召回，不擅长表达业务意义上的「相关」

**问题：** 检索排序异常，标题精确命中的文档排不上来。
**原因：** ngram 相关度偏好长文档，长文档被无关二元组推高。
**解决：** 数据库只负责召回（放大 6 倍取候选），应用层重新打分并本地分页。

**经验教训：** 数据库的相关度是**统计意义上**的相关，不等于**用户意义上**的相关。
把「召回」与「排序」的职责解耦，是提升检索质量的通用思路——搜索引擎如此，RAG 的混合检索
（RRF 只依赖排名、不依赖分数可比）同样如此。

### 4.4 字符串处理要「先规划、后落笔」

**问题：** 高亮标签嵌套错乱（`<mark><mark>…`）。
**原因：** 逐词替换让后插入的标签污染了前面的匹配。
**解决：** 改为单趟扫描、先收集区间再合并、最后统一插入标签。

**经验教训：** 对文本做「可能相互影响」的多次修改时，不要边扫描边修改；先**计算出完整的
修改方案（区间集合）**，再一次性应用。这与 diff 算法「先求 LCS 再回溯生成操作序列」的
思路是一致的。

### 4.5 前端细节同样会造成「功能不可用」

**问题：** 图表容器高度为 0，图表不显示。
**原因：** `height="560"` 传入的是无单位字符串，`height: 560` 是非法 CSS，被浏览器丢弃。
**解决：** 归一化补 `px` 单位。

**经验教训：** 一个看似微不足道的细节（CSS 单位）就能让整个图表「消失」。前端问题往往
**不报错、只不显示**，因此更需要自动化界面测试来捕捉——`ui_check.mjs` 统计 `canvas` 数量、
收集 `pageerror` 与失败请求，正是为此设计。

### 4.6 统计口径必须全局一致

**问题：** 发布趋势中已逻辑删除的条目仍计入「发布」曲线。
**原因：** 趋势统计遗漏了逻辑删除过滤。
**解决：** 统一过滤 `deleted`，与总览、分布等口径对齐。

**经验教训：** 逻辑删除引入后，**所有**统计查询都必须显式过滤删除标记。这类问题不会报错，
只会让数字「静默地错」，因此需要把过滤条件收敛为统一的查询约束，而不是在每个统计里各写一遍。

## 5 收获与不足

### 5.1 收获

1. **完整走通了软件工程的全过程**：从需求分析、概念与逻辑设计、编码实现到测试验收，
   把《软件工程》与《数据库原理》的知识落到了一个真实系统上。
2. **理解了「设计决策要有理由」**：无论是选 MySQL 全文索引而非 Elasticsearch，还是
   向量存 BLOB 而非向量库，每个决策都写清了取舍——技术选型不是选「最先进的」，而是选
   「最合适的」。
3. **掌握了知识建模的方法**：用「层次树 + 语义关系」双结构表达领域知识，并让结构真正
   **产生价值**（推理、查询扩展、自动标注、覆盖率度量），而不只是画一张图。
4. **具备了工程化的质量意识**：自动化接口测试与界面测试让「改完不放心」变成「一键验证」，
   也让答辩前的环境自检有了可靠手段。
5. **锻炼了协作与项目管理能力**：模块划分、接口冻结、进度跟踪与风险应对都在真实约束下
   演练了一遍。

### 5.2 不足

1. **本地向量模型能力有限**：默认的本地哈希向量模型是词汇级匹配，不具备真正的语义理解；
   语义能力依赖可选的在线模型。
2. **向量检索为内存暴力比对**：当前规模下可行，但缺乏 ANN 索引，规模增长后需要替换。
3. **本体自动抽取覆盖有限**：实体链接基于「词典 + 别名」匹配，对长尾概念与未登录词的
   召回有限，且依赖人工维护词典与别名。
4. **RAG 为单轮检索**：无法回答需要跨多个文档综合、经多跳推理才能回答的问题。
5. **测试以黑盒为主**：白盒覆盖集中在核心链路，尚无持续集成与自动回归的完整流水线。

## 6 后续可改进方向

| 方向 | 具体设想 | 预期收益 |
|---|---|---|
| **接入真实语义向量模型** | 将默认向量模型替换为中文语义向量模型（如 BGE 系列），或提供混合向量策略 | 填平「词汇鸿沟」，提升语义召回 |
| **引入 ANN 索引** | 以 HNSW / IVF 等近似最近邻索引替代内存暴力比对，或接入向量数据库 | 支持十万级以上分块的近邻检索 |
| **多跳检索与查询分解** | 把复杂问题拆成子问题、迭代检索与重排，逐步综合答案 | 回答需要跨文档推理的问题 |
| **本体自动抽取** | 从文本中自动抽取候选概念与关系，经人工复核后并入本体 | 降低本体维护成本，扩展长尾概念 |
| **协作编辑与变更通知** | 多人实时编辑、版本冲突提示与订阅通知 | 支持多人协同维护知识库 |
| **持续集成与自动回归** | 把两个测试脚本接入 CI，每次提交自动运行并留存报告 | 更早发现回归，提升质量保障水平 |
| **权限与审计细化** | 细粒度到分类 / 条目的授权，审计日志支持导出 | 适应更正式的组织使用场景 |

**结语式的自我判断：** 本系统在一个受限的课程设计周期内，完成了从知识建模到智能检索的
完整闭环，并把「可访问性」「可降级」「可核对」作为硬约束落实到了实现中。它证明了：
即使不引入重型中间件，只要**模型设计得当、职责划分清晰**，一套基于 MySQL 的知识管理系统
同样可以提供可靠、可解释、可演示的智能检索与问答能力。
