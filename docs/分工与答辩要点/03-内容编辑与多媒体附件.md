## 三、必须掌握的知识点

### 3.1 浏览器 Multipart 上传与 Spring `MultipartFile`

**是什么** —— 浏览器用 `multipart/form-data` 编码把文件二进制与普通表单字段拼在同一个请求体里，各段之间以 boundary 分隔。控制器用 `@RequestParam("file") MultipartFile` 或 `List<MultipartFile>` 接收，`MultipartFile` 提供 `getOriginalFilename()`、`getSize()`、`getContentType()`、`getInputStream()`。

**本系统怎么用的** —— `FileController` 提供 `/api/files/upload`（单文件）与 `/api/files/upload-batch`（`List<MultipartFile>`），受 `@PreAuthorize("hasAnyRole('ADMIN','EDITOR')")` 保护。`application.yml` 里 `spring.servlet.multipart` 设 `max-file-size: 300MB`、`max-request-size: 600MB`、`file-size-threshold: 2MB`（小于 2MB 的请求体缓存到内存，超过则落临时文件）。前端 `KnowledgeEditView` 用 Element Plus 的 `<el-upload>` 直传，`action` 指向 `fileApi.uploadUrl`，并在 `beforeUpload` 里先做一次扩展名与大小预校验。

**为什么这么做** —— 把 `max-request-size` 设为 `max-file-size` 的两倍，是给批量上传留余量（单个仍受 300MB 约束）。`file-size-threshold` 设 2MB 是为了小图小文档不进磁盘临时文件、大文件不全量占堆内存。若把 `max-request-size` 调得过大或 `max-swallow-size` 设为 `-1`（本项目确实如此），在拒绝超大请求时需要把请求体读完，会带来带宽与内存开销。

**可能被追问** —— Q：上传一个 500MB 的文件会怎样？
A：请求在进入控制器前就被 Spring 的 multipart 解析器拒绝（`max-file-size` 300MB），返回 413/异常，业务代码不会执行。即便改大配置放到控制器，`store` 里还有第二道 `file.getSize() > limit` 校验。

### 3.2 扩展名白名单校验与 MIME 类型判定

**是什么** —— 白名单（allow-list）是只放行已知安全的集合，比黑名单更可靠；MIME 类型是标准化的媒体类型标识（如 `application/pdf`）。

**本系统怎么用的** —— 白名单配置在 `application.yml` 的 `kms.storage.allowed-extensions`，按媒体类型分组：`DOCUMENT`（`pdf,doc,docx,ppt,pptx,xls,xlsx,txt,md,csv,json,xml`）、`IMAGE`（`png,jpg,jpeg,gif,bmp,webp,svg`）、`VIDEO`（`mp4,webm,mov,avi,mkv`）、`AUDIO`（`mp3,wav,m4a,aac,ogg`）。`FileStorageService.resolveMediaType(ext)` 遍历这张表做匹配，命中即返回组名（`DOCUMENT`/`IMAGE`/…），未命中直接抛 `FILE_ERROR`；返回的组名写入 `kb_attachment.media_type`。浏览器上报的 `file.getContentType()` 单独存进 `mime_type`；`storeBytes` 场景没有浏览器，则用 `guessMimeType(ext)` 按扩展名推断，另有 `guessMediaTypeByMime` 作为无扩展名时的兜底。

**为什么这么做** —— 扩展名来自用户可控的 `originalFilename`，因此白名单是**第一道**也是**主要**的准入关卡；`contentType` 同样由浏览器给出、可被伪造，所以只作为展示/预览提示，不参与安全判定。做法失效的条件：攻击者把可执行文件改名成 `x.pdf` 能通过扩展名检查，但该文件落到 UUID 命名的存储目录、无法被当作脚本执行（且未做服务端内容嗅探）。若要更严，应叠加文件头 magic number 校验。

**可能被追问** —— Q：只看扩展名够安全吗？
A：在本系统的部署形态下足够——上传目录不在 Web 根、文件名被 UUID 重写、浏览器按 `Content-Type` 与 `Content-Disposition` 处理。约束是它不防"内容与扩展名不符"的欺骗，属于已知取舍。

### 3.3 路径穿越攻击与防御

**是什么** —— 路径穿越（path traversal，`../` 攻击）指攻击者构造含 `..` 的文件名或路径参数，使程序拼出的路径跳出预期目录，读到或写到系统任意位置。经典形式是文件名 `../../../../etc/passwd`。

**本系统怎么用的** —— 三重防御：① 入口处 `Paths.get(file.getOriginalFilename()).getFileName().toString()` 只取最后一段，直接丢掉任何目录成分；② 存储名完全由程序生成——`UUID.randomUUID()` 去掉横线加扩展名，用户输入不参与路径拼接；③ 拼出目标后 `storageRoot().resolve(relativePath).normalize()`，再断言 `target.startsWith(storageRoot())`，否则抛"非法的文件路径"。同样的 `normalize()` + `startsWith` 检查在读取侧的 `resolve(String relativePath)` 里再做一遍，因为下载接口的路径参数来自 URL。

**为什么这么做** —— `normalize()` 会把 `a/../b` 折叠成 `b`、把 `..` 向上消除，**必须先 normalize 再 startsWith**：如果顺序反过来，一个含 `..` 的未规范化路径在字符串上仍以 root 开头，检查会形同虚设；normalize 之后若真的跳出了 root，`startsWith` 才能识别。失效条件：该检查**不防符号链接**——若攻击者能在存储目录内预先放置一个指向外部的软链接并在路径中使用它，`normalize` 不会解析链接。本项目上传目录由服务独占，未开放建链接能力，故未叠加 `toRealPath()` 校验。

**可能被追问** —— Q：为什么 `normalize()` 之后还要检查 `startsWith(root)`？
A：normalize 负责把 `..` 消掉、暴露出真实层级，startsWith 负责判定这个真实层级是否仍在根目录内；两步缺一不可——只 normalize 不检查，跳出 root 也无人发现；只检查不 normalize，含 `..` 的字符串照样骗过前缀判断。

### 3.4 文件存储布局设计

**是什么** —— 存储布局指物理文件在磁盘上的组织方式，常见有"全平铺在一个目录"与"分层散列/按时间分目录"两种。

**本系统怎么用的** —— `FileStorageService.MONTH_DIR = "yyyy/MM"`，每个文件落在 `<root>/yyyy/MM/<uuid>.<ext>`，例如 `2026/10/3f9a...c1.pdf`；`kb_attachment.file_path` 存的是**相对 root 的路径**，绝对位置由 `storageRoot() + file_path` 还原。原始文件名存 `file_name`，另起 `stored_name` 保存 UUID 名。存储根由 `kms.storage.root` 配置，默认 `../storage`（相对后端进程工作目录）。

**为什么这么做** —— 按年月分目录，避免单目录堆积成千上万个文件导致目录项检索与 `ls` 变慢；按时间分也方便按批次备份/清理。用 UUID 替换原文件名有两个作用：一是**避免同名覆盖**（两个用户传同名文件不会互相顶掉），二是**避免文件名泄露信息**并从根上消除路径穿越。存储相对路径则让整个 `storage/` 目录可整体迁移而不必改库。失效条件：`root` 是相对路径，**进程工作目录决定它指向哪里**——启动脚本先 `cd backend/` 再启动以保证落在 `kms/storage`；若在别的目录执行 jar，附件会被写到别处，表现为"之前上传的文件不见了"且不报错，因此 `storageRoot()` 首次解析时会把绝对路径打进日志。

**可能被追问** —— Q：为什么用 UUID 而不是沿用原文件名？
A：防重名覆盖、防文件名信息泄露、防路径穿越；代价是磁盘上文件名不可读，但原始名保留在库里，展示与下载都用 `file_name`，不影响使用。

### 3.5 多格式正文抽取的实现

**是什么** —— 正文抽取（text extraction）是从二进制文档里取出可读文本，使其能被索引与检索，区别于"仅能下载查看"。

**本系统怎么用的** —— `FileTextExtractor.extract(path, ext)` 用 `switch` 分派：PDF 用 PDFBox 的 `Loader.loadPDF` + `PDFTextStripper`（`setSortByPosition(true)` 按坐标排序，避免多栏串行）；`.docx` 用 POI 的 `XWPFWordExtractor`，`.doc` 用 `HWPFDocument` + `WordExtractor`；`.xlsx` 用 `XSSFWorkbook`、`.xls` 用 `HSSFWorkbook`，按工作表逐行逐单元格取值（数值、日期、布尔、公式各有分支）；`.pptx`/`.ppt` 用 `XMLSlideShow`/`HSLFSlideShow` 遍历每张幻灯片的文本形状；`txt/md/csv/json/xml` 等纯文本直接读，其中 Markdown 用 commonmark 的 `Parser` + `TextContentRenderer` 去标记，HTML 用 `stripHtml` 去标签。结果经 `TextUtils.normalizeWhitespace` 压缩空白，并截断到 `MAX_CHARS = 400_000`。图片、音视频落入 `default` 分支返回 `UNSUPPORTED`。

**为什么这么做** —— 每种格式独立 `try/catch`，单个文件解析失败只把该附件标 `FAILED`，不拖垮整体上传；400k 字符上限防止超大文档把内存与索引拖垮；`setSortByPosition(true)` 是针对 PDF 表格/多栏的常见补救。失效条件：扫描版 PDF（图片型）没有文字层，PDFBox 抽不出内容，会被判为 `UNSUPPORTED`——需要 OCR，本系统未引入。

**可能被追问** —— Q：为什么 Markdown 要专门"去标记"？
A：Markdown 里的 `#`、`**`、表格竖线、代码围栏不是正文，直接入库会污染检索词项。用 commonmark 解析成 AST 再渲染为纯文本，得到的是读者真正看到的内容。

### 3.6 为什么"文件存在"不等于"文件内容可被检索"

**是什么** —— 文件被存到磁盘、库里有一条 `kb_attachment` 记录，只说明"文件在"，不代表它的**文字**进入了检索索引。

**本系统怎么用的** —— 检索链路读的是 `kb_attachment.extracted_text`（以及条目的 `plain_text`），而索引是 `kb_attachment` 上的 ngram 全文索引 `ft_att_ngram(file_name, extracted_text)`。因此 `store` 与 `storeBytes` 在落盘后**同步**调用 `textExtractor.extract`，把文本写进 `extracted_text`、把状态写进 `extract_status`。只有 `extract_status = SUCCESS` 的附件，其内容才可被搜到；`UNSUPPORTED`（图片/音视频）与 `FAILED` 的附件只能下载，搜不到正文。前端会明确提示"该格式不支持抽取正文，仅供下载"。

**为什么这么做** —— 把"能不能搜"做成一个显式状态而非隐式假设，用户和答辩老师都能一眼看懂；也解释了"我传了 PDF 却搜不到"这类问题的根因（可能是扫描件、抽取失败或未成功保存）。失效条件：若抽取在入库后异步进行，就会出现"上传成功但暂时搜不到"的时间窗；本系统选择同步抽取以消除这个窗口——代价是大文件上传请求会因解析而变慢。

**可能被追问** —— Q：上传了一个图片，为什么搜不到图中的字？
A：图片走 `default` 分支，`extract_status` 记为 `UNSUPPORTED`，`extracted_text` 为空，不进入 ngram 索引。要支持图片内文字需要 OCR，不在本系统范围。

### 3.7 HTTP Range 请求与视频拖动进度条

**是什么** —— HTTP Range 是"仅请求资源的一段字节"的机制：客户端发 `Range: bytes=1000000-`，服务器若支持则回 `206 Partial Content` 加 `Content-Range`，否则回 200 全量。视频拖动进度条依赖它——播放器只需拉取目标时间点附近的字节，不必下载整个文件。

**本系统怎么用的** —— `FileController.preview` 对非下载请求显式设置 `Accept-Ranges: bytes` 与 `Cache-Control: public, max-age=86400`，返回 `ResponseEntity<Resource>`（`FileSystemResource`）。前端用 `<video src>` 直接引用该地址，浏览器据此发起 Range 请求实现拖动。下载分支则走 `Content-Disposition: attachment`，不做内联播放。

**为什么这么做** —— 声明 `Accept-Ranges` 是让浏览器知道"可以按段取"，这是进度条可拖动的必要条件；`max-age` 让同一视频二次播放命中浏览器缓存，减少重复传输。失效条件：若服务器不真正支持断点（不回 206），拖动会退化为重新请求整个文件，体验上表现为"拖不动/卡住"。

**可能被追问** —— Q：同一个接口为什么能既预览又下载？
A：用 `download` 布尔参数分支：`download=true` 时设 `Content-Disposition: attachment` 触发浏览器下载；否则内联渲染。资源本体相同，只是响应头不同。

### 3.8 `Content-Disposition` 与中文文件名编码

**是什么** —— `Content-Disposition` 告诉浏览器把响应当"内联显示"还是"另存为附件"。文件名若含中文，必须用 RFC 5987 的 `filename*=UTF-8''<百分号编码>` 形式，否则在 `ISO-8859-1` 头里会乱码。

**本系统怎么用的** —— 下载时 `FileController` 先 `URLEncoder.encode(fileName, UTF_8)`，再把 `+` 替换回 `%20`（`URLEncoder` 会把空格编成 `+`，而 RFC 5987 要求 `%20`），最后拼成 `attachment; filename*=UTF-8''<encoded>`。存库的 `file_name` 保留可读中文原名，下载文件名即由它编码而来。

**为什么这么做** —— 只写 `filename=` 会因响应头默认字符集丢中文；用 `filename*=` 显式声明 UTF-8 才是浏览器普遍支持的写法。`+` → `%20` 是易错点：不替换时文件名里的空格会被解码成加号。

**可能被追问** —— Q：为什么库里同时存 `file_name` 和 `stored_name`？
A：`file_name` 是给人看的原始名（可能重复、可能含中文、可能含 `..`），只用于展示与下载头；`stored_name` 是磁盘上的 UUID 名，只用于定位文件。职责分离，安全与可读性各得其所。

### 3.9 审计日志的异步记录与独立事务（`REQUIRES_NEW`）

**是什么** —— 审计日志记录"谁在什么时候对什么做了什么"。默认事务传播 `REQUIRED` 会加入调用方事务，导致主业务回滚时审计一起回滚；`REQUIRES_NEW` 则**挂起当前事务、另开一个新事务**提交。

**本系统怎么用的** —— `AuditService.record` 标注 `@Async` 与 `@Transactional(propagation = REQUIRES_NEW)`：异步让记录不阻塞用户请求，独立事务保证它与主业务互不牵连。方法体整体包在 `try/catch` 里，审计失败只 `log.warn`，绝不影响业务。字段上 `userId/username` 取自 `SecurityUtils`，`ip` 优先取 `X-Forwarded-For` 的第一段、否则 `remoteAddr`，`detail` 截断到 1000 字符。另有 `recordSync` 供需要"立即落库"的场景使用。

**为什么这么做** —— 审计的价值在于**忠实**：如果主事务回滚把审计也带走，就丢失了"这次失败尝试发生过"的证据；反之主业务也不应因审计写库失败而被拖垮。异步 + 独立事务同时满足"不阻塞"与"不被回滚"。失效条件：`@Async` 依赖线程池，若线程池被占满，日志会延迟；`SecurityUtils` 依赖 `RequestContextHolder`，在异步线程里拿不到请求上下文，因此 `currentIp()` 内部做了空判与 `try/catch` 兜底。

**可能被追问** —— Q：既然异步，`SecurityUtils.currentUserId()` 还能取到当前用户吗？
A：能——`record` 被调用时仍在请求线程内，用户信息在方法进入时即被读取；只有 `currentIp()` 依赖 `RequestContextHolder`，在真正的异步执行线程里可能为空，所以做了 null 兜底。

### 3.10 归档与删除的区别、审计的不可篡改性

**是什么** —— **删除**是从系统中移除；**归档**是把内容移出常规范围但完整保留，可追溯、可恢复。**不可篡改**指审计记录只增不改不删。

**本系统怎么用的** —— 归档由 `KnowledgeItemService.archive` 实现：状态置 `ARCHIVED`，写入 `archived_at` 与 `archive_reason`，并发布 `ItemChangedEvent.archived`；`unarchive` 把状态**恢复为 `DRAFT`（草稿）而非直接 `PUBLISHED`**，清空归档字段。归档条目不再进入常规检索——查询拼装处显式 `notEqual(status, ARCHIVED)`，`ArchiveView` 是唯一集中查看归档的入口。删除则是逻辑删除（`deleted = 1`），条目从列表消失但行仍在库中。审计侧，`AuditLog` 实体无更新/删除入口，Repository 只暴露查询与 `save`，`AuditController` 整体 `@PreAuthorize("hasRole('ADMIN')")` 且只有 GET。

**为什么这么做** —— 归档保留正文、附件与版本历史，符合"知识资产只增不减"的治理理念，归档原因本身也是信息（说明"这份资料为何不再推荐"）。恢复回草稿而非直接发布，是因为归档通常意味内容可能过时，需要编辑重新确认后再发布。审计表不提供改删接口，是"不可篡改"在应用层的最小落地；更强的做法是只追加、写入独立存储或做哈希链，本系统未做到那一层。

**可能被追问** —— Q：归档和删除，用户会混淆吗？系统怎么区分？
A：`MyContentView` 里"归档"与"删除"是两个独立按钮，归档要填**原因**、删除要二次确认；数据库层 `status = ARCHIVED` 与 `deleted = 1` 是两个不同字段，前者可 `unarchive` 恢复，后者是逻辑删除不出现在任何列表。

### 3.11 Markdown 内容编辑器与"编辑态—发布态"

**是什么** —— 本系统正文以 Markdown 存储，而非富文本 HTML；编辑器需要兼顾"看得见格式"与"存得下结构化文本"。

**本系统怎么用的** —— `KnowledgeEditView` 用大号 `textarea` 编辑 Markdown，提供"预览"开关切到 `MarkdownView` 组件渲染；正文以外还有摘要、资产类型、分类、标签、来源、知识点标注、附件、版本说明等字段。保存时 `markdownToPlain` 抽取纯文本供检索；摘要留空会从正文自动截取前 180 字符；`dirty` 计算属性跟踪未保存改动，并注册 `beforeunload` 作最后一道防线。保存动作分"保存修改""保存并发布（要求填发布说明）""保存为草稿并返回"三种。

**为什么这么做** —— 存 Markdown 而非 HTML，检索时无需再剥离标签，纯文本天然干净，也便于版本差异比对。编辑器不引入重型所见即所得组件，是因为本课题内容以技术文档为主、Markdown 表达力足够，且减少前端复杂度。失效条件：Markdown 的表格/公式等复杂语法在纯 textarea 里无语法高亮，写作体验弱于专用编辑器，属于刻意取舍。

**可能被追问** —— Q：为什么正文不直接存纯文本，还要留 Markdown？
A：纯文本会丢失标题、列表、表格等结构，展示时无法还原；检索用的是另存的 `plain_text`，两者分工——Markdown 面向展示与版本差异，纯文本面向检索。

## 四、答辩预设问答

**Q：上传接口谁能调？下载接口谁都能调吗？**
A：`/api/files/upload`、`upload-batch`、`DELETE /{id}` 受 `@PreAuthorize("hasAnyRole('ADMIN','EDITOR')")` 限制；`GET /api/files/preview/**` 在 `SecurityConfig` 里 `permitAll`，便于 `<img>`、`<video>` 直接引用，`GET /{id}` 详情与白名单接口也不需写权限。

**Q：白名单在配置里改一个扩展名，需要动代码吗？**
A：不用。白名单在 `application.yml` 的 `kms.storage.allowed-extensions`，改配置重启即生效；`FileController` 的 `/allowed-extensions` 接口把它读出来，前端可据此与后端保持一致。

**Q：抽取正文是同步还是异步？为什么？**
A：同步——在 `store` / `storeBytes` 落盘后立即调用 `FileTextExtractor.extract`。这样附件一入库就已可检索，不存在"传完暂时搜不到"的窗口；代价是大文件上传响应会因解析而变慢。

**Q：抽取失败和格式不支持，状态怎么区分？**
A：`extract_status` 有 `SUCCESS` / `FAILED` / `UNSUPPORTED` 三态（初始 `PENDING`）。图片音视频返回 `UNSUPPORTED`（`default` 分支）；解析抛异常走 `catch` 返回 `FAILED`；抽到但内容为空也归 `UNSUPPORTED`。

**Q：11 个演示附件是怎么来的？为什么不在仓库里放二进制文件？**
A：由 `SampleFileFactory` 在初始化时**现场生成**——3 个 PDF、3 个 PNG（架构图、E-R 图、本体全景图）、1 个 DOCX、2 个 XLSX、2 个 Markdown，共 11 个。这样仓库保持轻量，且生成内容与知识条目一一对应、可被检索命中。PDF 用系统字体 `simhei.ttf` 嵌入中文，找不到时降级为英文占位。

**Q：`storeBytes` 和 `store` 有什么区别？**
A：`store` 从 `MultipartFile` 取字节（HTTP 上传），`storeBytes` 直接接收 `byte[]`（程序生成）。两者共用同一套存储布局、UUID 命名与正文抽取逻辑，只是入口不同；`storeBytes` 的 MIME 由 `guessMimeType(ext)` 推断。

**Q：附件和知识条目是怎么绑定的？可以先传后挂吗？**
A：可以。`kb_attachment.item_id` 允许为空（先上传拿到 id，再在保存条目时通过 `attachmentIds` 调用 `AttachmentRepository.bindToItem` 挂载）。删除条目时外键 `fk_att_item ... ON DELETE CASCADE` 会带走附件记录。

**Q：附件删除时物理文件也会删吗？**
A：会。`FileStorageService.delete` 先 `Files.deleteIfExists(stored)` 删物理文件，再删库记录；物理删除失败只 `log.warn` 不中断，避免"文件删不掉导致记录也删不掉"。

**Q：审计日志的查询支持哪些条件？**
A：`AuditLogRepository.search` 支持按 `action`、`targetType`、`username`（模糊）、时间范围 `from/to` 组合过滤，按 `id desc` 分页；`AuditController` 全部要求 `ADMIN` 角色。前端 `AuditLogView` 还提供"导出当前页为 CSV"，写入 UTF-8 BOM 以免 Excel 打开中文乱码。

**Q：审计里的 `action` 和 `target_type` 存的是编码，界面怎么显示中文？**
A：`AuditLogView` 里维护 `ACTION_TEXT` 与 `TARGET_TEXT` 两张翻译表，覆盖 CREATE/UPDATE/DELETE/PUBLISH/UNPUBLISH/SUBMIT/ARCHIVE/UNARCHIVE/ROLLBACK/CREATE_VERSION/LOGIN/REGISTER/CHANGE_PASSWORD 与 ITEM/CONCEPT/RELATION/CATEGORY/USER/POLICY；翻译表与首页看板动态流保持一致，避免同一动作两种叫法。

**Q：归档的条目还能被检索到吗？**
A：不能。条目查询条件里显式排除 `status = ARCHIVED`；归档内容只在 `ArchiveView` 里检索与恢复。这保证了常规检索与问答的信噪比。

**Q：恢复归档后是直接发布吗？**
A：不是，回到 `DRAFT`。归档往往意味着内容可能已过时，需编辑确认后再走发布流程；`ArchiveView` 的确认框也把这一点写给用户看。

**Q：如果审计写库失败了会怎样？**
A：`AuditService.record` 全程 `try/catch`，失败只记 `log.warn`，不影响主业务返回；这是"审计失败不阻断业务"的刻意设计。

**Q：存储根目录是相对路径，有什么坑？**
A：`kms.storage.root = ../storage` 相对**进程工作目录**解析。启动脚本保证先 `cd backend/`；若换方式启动（如项目根目录直接 `java -jar`），附件会落到别处且不报错，表现为"之前传的文件不见了"。因此 `storageRoot()` 首次解析时把绝对路径写进日志，便于排查。

**Q：视频附件支持在线播放吗？**
A：支持。音视频在白名单内，预览接口返回 `Accept-Ranges: bytes`，前端用 `<video>` 内联播放并支持拖动进度条；但音视频不做正文抽取（`UNSUPPORTED`），不会被检索命中。
