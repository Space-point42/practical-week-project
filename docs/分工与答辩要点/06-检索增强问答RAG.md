## 三、必须掌握的知识点

### 3.1 什么是 RAG，为什么需要它

**是什么**：RAG（Retrieval-Augmented Generation，检索增强生成）先检索出与问题相关的资料，
再把资料作为上下文交给大模型生成回答。它把"知识"与"语言能力"分开：
检索提供事实依据，生成模型负责组织语言。

**本系统怎么用的**：`RagService.ask()` 是完整的五步流程——
① 本体查询扩展 → ② 双通道混合检索 → ③ 上下文组装 → ④ 生成 → ⑤ 会话落库。

**为什么这么做**：不检索直接问大模型，它不知道我们课程知识库里有什么；
把整个知识库塞进提示词又会超出上下文窗口且成本高昂。
RAG 只取最相关的几个片段，既控制了上下文规模，又让回答**可溯源**——这是知识库场景最看重的性质。

**可能被追问**：RAG 与直接用大模型问答的区别是什么？
答：区别在于事实来源。直接用大模型靠模型自身的参数化记忆，会编造；
RAG 的每个结论都来自检索到的资料，可以逐条核对原文。

### 3.2 文本分块

**是什么**：把长文档切成若干语义相对完整的片段，以片段作为检索的最小单位。

**本系统怎么用的**：目标块长 **420 字符**，相邻块重叠 **80 字符**（约 19%）。
切分优先级是 **段落边界 > 句子边界（。！？；）> 长度硬切**：
先按空行切自然段，段落超长再按句末标点切，只有连句子都过长时才按长度硬切。
单块上限控制在 500 字符左右。

**为什么这么做**：块太大则噪声多、向量语义被"平均"掉，检索精度下降；
块太小则上下文不足，完整论述被割裂。
重叠窗口的作用是防止关键信息正好落在切分点上——
例如某个定义的完整表述跨越两块边界时，重叠能保证至少一块包含完整定义。

**可能被追问**：重叠会不会造成重复召回？
答：会。同一段内容可能被多个块命中，所以组装上下文时还需要按条目去重，
这一步在 `RagService.buildContexts()` 中用 `seenChunks` 集合完成。

### 3.3 文本向量化

**是什么**：把文本映射为固定维度的稠密向量，使语义相近的文本在向量空间中距离更近。

**本系统怎么用的**：`EmbeddingService` 是统一门面，下挂两个实现：
- `LocalHashingEmbedding`：**离线可用**。抽取 jieba 分词结果 + 字符 n-gram 作为特征，
  用哈希把特征映射到 512 维桶中，并用第二个哈希位决定符号（signed hashing，降低冲突偏差），
  权重取 sublinear TF `1 + ln(tf)`，最后 L2 归一化。
- `OpenAiEmbedding`：调用 OpenAI 兼容的 `/embeddings` 接口，接入任意兼容服务。

系统默认用本地模型，配置 API Key 后自动切为在线模型。
向量以 **float32 小端序列**存入 `rag_chunk.embedding`（MEDIUMBLOB），比 JSON 文本省约 4 倍空间。

**为什么这么做**：本地哈希向量**零外部依赖**，保证系统在任何环境下都能离线运行；
但它的本质是**词汇级匹配**，不具备同义扩展能力 ——
这一点必须如实说明，不能把它包装成"语义向量"。
真正的语义理解交给在线向量模型或上层的大模型。

**可能被追问**：切换向量模型要注意什么？
答：**必须重建全部索引**。不同模型产出的向量不在同一向量空间，跨模型比较没有意义。
系统为此在每个分块上记录了 `embed_model` 与 `dim`，检索时只与维度一致的向量比较，
并在"检索索引"页列出"过期模型"提示管理员重建。

### 3.4 混合检索与 RRF 融合

**是什么**：同时用两条通道召回——**向量通道**按语义相似度、
**关键字通道**按词面命中——再把两条通道的排名融合成一个最终排名。

**本系统怎么用的**：两条通道各取 Top-20 候选。
融合用**倒数排名融合（RRF）**：`score = Σ 1/(k + rank)`，常数 `k = 60`；
关键字通道的结果额外乘以 **1.15** 的权重。
`HybridRetriever.retrieve()` 同时保留每条候选在各通道中的排名与得分，
这也是界面能展示"检索过程明细"的前提。

**为什么这么做**：两条通道的失败模式不重叠 ——
向量通道擅长处理"问法与原文用词不同"，但精度低、易召回泛泛而谈的内容；
关键字通道精确但无法处理同义改写。
组合后整体优于任一单通道。

**为什么不直接相加分数**：余弦相似度落在 0~1 之间，BM25 相关度可能是 0~30，
两者量纲完全不同，加权求和需要大量调参且不稳定。
RRF 只用排名、不用分数，天然规避了这个问题。

**直观例子**：文档 A 向量通道排第 1、关键字通道排第 10；文档 B 两条通道都排第 3。
取 k=60：A 得 `1/61 + 1/70 ≈ 0.0307`，B 得 `1/63 + 1/63 ≈ 0.0317` —— B 胜出。
**RRF 奖励"两条通道都认可"的文档**，而不是"某一条通道特别认可"的文档。

**可能被追问**：k 取 60 的依据是什么？
答：k 是平滑常数。k 越大各排名的差距被拉平得越多，k 越小头部排名优势越突出。
60 是信息检索领域的经验值，在本系统的语料规模下表现稳定。

### 3.5 本体查询扩展（本系统的特色）

**是什么**：在检索之前，先用实体链接识别出问题中的知识点，
再沿本体关系补充相邻概念，把这些词一并拼入检索串。

**本系统怎么用的**：`RagService.expandQuery()` 调用 `OntologyService.link()` 做实体链接，
再调用 `OntologyService.expand()` 沿 `SUB_CLASS_OF`、`PART_OF`、`PREREQUISITE_OF`、`RELATED_TO`
四类关系扩展，上限 6 个概念。

例：用户问"需求分析怎么做" → 实体链接命中「需求分析」→
沿关系扩展出「需求获取」「需求验证」「需求规格说明」→
检索串变为"需求分析怎么做 需求获取 需求验证 需求规格说明"。

**为什么这么做**：一般的 RAG 直接用用户原话检索。
但课程知识本身具有清晰的结构（先修、组成关系），
把结构信息注入检索可以弥补纯向量方法的不足。界面在"检索过程"面板中会列出扩展出的概念。

**可能被追问**：扩展会不会引入噪声？
答：会，所以限制了参与扩展的关系类型（只取语义距离近的四类）和扩展数量上限（6 个），
并且扩展词是**追加**到原查询之后而不是替换，原始查询的权重仍然保留。

### 3.6 上下文组装与提示词

**是什么**：把检索到的片段组织成能被大模型正确引用的提示词。

**本系统怎么用的**：`buildMessages()` 按 `【来源 1】《标题》（资产类型）` 的格式拼接片段，
每块截断至 1,200 字符，最后附上用户问题；
`systemPrompt()` 给出五条约束，最关键的两条是
"只依据【来源】中提供的资料作答，不要引入资料之外的推测"
与"在每个结论后用【来源 N】标注依据"。

**为什么这么做**：给片段编号是让模型能正确引用、也让用户能核对的前提。
限制知识边界是抑制幻觉最有效的一句话。
片段顺序按相关度排列，重要的放前面——模型对前文更敏感。

**可能被追问**：怎么防止模型编造？
答：三重措施——提示词限定知识边界、要求标注来源、以及引用列表会原样附在回答下方供用户核对。
另外当知识库确实没有相关内容时，系统直接返回"未找到"而不是让模型硬答。

### 3.7 引用溯源

**是什么**：在回答中标注每个结论的依据来源，并允许用户跳转到原文。

**本系统怎么用的**：每条引用记录条目 id、块 id、片段摘要、融合得分，
以及它在两条通道中的**排名**（如"向量 #1 · 关键字 #2"）。
前端点击引用直接跳转到知识详情页。

**为什么这么做**：三个理由——
可信度（用户可以核对结论是否真的成立）、
可追责（出错的结论能定位到具体来源，便于修正语料）、
可学习（用户顺着引用读原文，往往比提问收获更多）。
展示通道排名是让用户判断这条引用的可信程度：两通道都排前面的比单通道的更可靠。

**可能被追问**：如果模型编造了一个引用编号怎么办？
答：编号是系统在组装上下文时赋予的，模型只能引用已存在的编号；
前端渲染时以系统保存的 `citations` 数组为准，模型文本里的编号即便写错也点不到不存在的来源。

### 3.8 降级设计：没有大模型也能回答

**是什么**：当未配置大模型接口或调用失败时，系统自动切换为**离线抽取式回答**。

**本系统怎么用的**：`ChatService.tryComplete()` 在不可用时返回 `null`，
`RagService.generate()` 转而调用 `ExtractiveAnswerBuilder.build()`：
从检索结果中按与查询词的重合度抽取最相关的句子，
逐条标注【来源 N】，并明确告知用户"当前为离线抽取式回答"。

**为什么这么做**：这是刻意设计的降级路径而不是兜底。
它**零幻觉、可逐句核对**，回答内容全部来自原文；
虽然语言不如大模型自然，但保证系统在断网环境下仍能完整演示问答的全部链路。
在答辩场景下，演示的确定性比回答的流畅度更重要。

**可能被追问**：这算不算"没有实现 RAG 的 G"？
答：RAG 的检索部分（R）是本系统自己实现的，包括分块、向量化、混合召回与融合；
生成部分（G）用的是外部大模型（通过 OpenAI 兼容接口调用，本项目配置的是 DeepSeek）。
之所以不自己训练模型，是因为课程设计的目标是掌握 RAG 这条流水线，
而不是重复造一个基座模型 —— 这本身也是一个工程取舍：
能用成熟服务解决的环节，就不应该自建。离线模式则是保证系统在没有外部依赖时依然可用的第二条路径。

### 3.8.1 本项目实际使用的生成模型与踩过的坑

当前配置（`application-local.yml`）：
`deepseek-flash`，`base-url: https://api.deepseek.com/v1`，
`max-tokens: 16000`，`reasoning-effort: low`。

**坑一：推理类模型的"只想了没答"。** 配置好 Key 之后第一次提问仍然返回了离线抽取式回答，
日志显示"生成接口返回了空回答"。排查后发现 `deepseek-flash` 是**推理类模型**：
它先输出思考过程（`reasoning_content`）再输出答案（`content`），
两者**共同**占用 `max_tokens`。当时额度设为 1500，被思考过程耗尽，答案就是空的，
且 `finish_reason` 为 `length`。更麻烦的是思考长度**是随机的** ——
同一个问题实测在 500 到 4000 tokens 之间浮动，所以它时好时坏。
解决：把 `max-tokens` 提到 16000（上限而非预留，按实际用量计费，留大不额外花钱），
并设置 `reasoning-effort: low` 降低思考开销（实测思考量近乎减半、响应时间显著下降，
而"依据资料归纳"这类任务的质量几乎不受影响）。

**坑二：错误信息把原因说错了。** 原来的提示是"生成接口返回了空回答"，
这会让人误以为是接口坏了或 Key 无效。修正为：检测到 `reasoning_tokens > 0`
或 `finish_reason = length` 时，明确报出"只返回了思考过程而未返回答案（推理消耗 N tokens）"，
并指向 `max-tokens` 这个真正需要调整的参数。**错误信息的准确性与功能本身同样重要** ——
不准确的报错会把排查引向错误的方向。

**坑三：提问被发送了两次。** `RagService.ask()` 会先把用户提问落库，
随后 `buildMessages()` 取最近若干轮历史时，取回的**最后一条正是本次提问**，
于是同一个问题在请求里出现两次。这既浪费上下文，也可能让模型误以为被追问了一次。
修正为：取历史时多取一条再判断，若末条与本轮问题相同则剔除。

### 3.9 索引的异步重建

**是什么**：内容变更后重建检索索引的过程在后台异步执行。

**本系统怎么用的**：知识库模块在保存/发布/回滚/归档时发布 `ItemChangedEvent`；
`RagIndexService.onItemChanged()` 用 `@Async` + `@EventListener` 异步接收，
然后 `reindexItem()` 在**独立事务**（`REQUIRES_NEW`）中"先删该条目的旧分块、再建新的"。

**为什么这么做**：向量化耗时较大（60 条知识 → 164 个分块约 1.2 秒），
同步执行会让用户的保存操作卡顿。
异步 + 事件解耦还带来一个好处：知识库模块不需要知道 RAG 的存在，依赖方向保持单向。
"先删后建"是为了幂等——无论之前索引处于什么状态，重建后一定与当前正文一致。

**可能被追问**：索引失败会影响用户保存吗？
答：不会。索引是派生数据，失败只记录日志，管理员可在"检索索引"页手动重建。

### 3.10 向量检索的实现方式与规模边界

**是什么**：相似度计算采用**暴力比对**（Brute-force），即把候选分块全部读入内存逐条计算余弦相似度。

**本系统怎么用的**：`HybridRetriever` 调用 `chunkRepository.findAllWithEmbedding()` 取出全部分块向量，
对每个分块计算 `EmbeddingService.cosine()`。向量已 L2 归一化，因此余弦相似度等于点积。

**为什么这么做**：164 个分块的暴力比对耗时在几十毫秒量级，
引入向量数据库带来的运维复杂度远大于它节省的时间。
**这个决策有明确的失效边界**：当规模达到百万级分块时暴力比对不再可行，
届时应当引入近似最近邻（ANN）索引，如 HNSW 或 IVF。
把这个边界写清楚，比单纯说"我们用了暴力比对"更有意义。

**可能被追问**：为什么不用向量数据库？
答：数据规模不够大，收益不抵成本。万级分块下暴力比对几十毫秒就够，
引入专用组件反而增加部署与运维负担，还多了一处数据一致性的隐患。

**Q：RAG 的全称是什么？它解决了什么问题？**
A：Retrieval-Augmented Generation，检索增强生成。解决的是大模型"不知道私有知识、
且容易编造"的问题：先从自有知识库检索出相关片段，再让模型基于这些片段回答。

**Q：你们的检索用了哪两条通道？为什么要用两条？**
A：向量通道（余弦相似度）和关键字通道（MySQL ngram 全文索引）。
两条通道的失败模式不重叠：向量通道能处理"问法与原文用词不同"，但精度低；
关键字通道精确但无法处理同义改写。组合后优于任一单通道。

**Q：RRF 是什么？为什么不用加权求和？**
A：倒数排名融合。公式是 `Σ 1/(k+rank)`，k 取 60。
不用加权求和是因为两个通道的分数不在一个量纲上——
余弦相似度是 0~1，全文相关度可能是 0~30，直接相加需要大量调参且不稳定。
RRF 只用排名，天然规避了这个问题。

**Q：分块的大小怎么定的？**
A：目标 420 字符、重叠 80 字符。这个取值是在"块太大导致向量语义模糊"
和"块太小导致上下文不足"之间的折中。重叠约 19%，落在常见的 10%~20% 区间内。

**Q：你们的向量是真正的语义向量吗？**
A：默认配置下不是。默认用的是本地哈希向量，它捕捉的是词汇层面的重叠，不具备同义扩展能力。
系统提供了在线语义向量模型的接口，配置 API Key 并重建索引即可切换。
我们在文档中如实标注了这一点，没有把它包装成语义向量。

**Q：为什么切换向量模型必须重建索引？**
A：因为不同模型产出的向量不在同一个向量空间，跨模型计算相似度没有意义。
系统在每个分块上记录了 `embed_model` 和 `dim`，检索时只与维度一致的向量比较，
并在索引状态页列出"过期模型"提示管理员重建。

**Q：什么是本体查询扩展？举个例子。**
A：在检索前先识别问题中的知识点，再沿本体关系补充相邻概念拼入检索串。
例如问"需求分析怎么做"，系统会扩展出"需求获取""需求验证""需求规格说明"，
这样相邻知识点的资料也能被召回。这是本系统区别于通用 RAG 的一处改进。

**Q：如果知识库里没有相关内容，系统会怎么做？**
A：如实说明"知识库中暂时没有找到与该问题相关的内容"并给出检索建议，
不会让大模型凭空回答。这一点在接口测试中有专门的断言验证。

**Q：检索到的片段怎么避免重复？**
A：分块有 80 字符的重叠，同一段内容可能被多个块命中，
因此在组装上下文时用 `seenChunks` 集合按块 id 去重。

**Q：索引重建为什么要用异步？事务怎么控制的？**
A：向量化耗时较大（60 条知识约 1.2 秒），同步会让用户保存时卡顿。
通过 Spring 事件 + `@Async` 异步执行，每个条目在独立事务（`REQUIRES_NEW`）中重建，
单条失败不影响整批。

**Q：为什么检索索引要"先删后建"而不是增量更新？**
A：为了幂等。无论之前索引处于什么状态，重建后一定与当前正文一致。
增量更新需要考虑"哪些块变了""块数量变了怎么办"等一堆边界情况，
容易被漏掉导致索引与正文不一致。

**Q：界面上的"检索过程"面板展示了什么？**
A：两条通道各自的候选数量、融合后的候选数、进入上下文的分块数、
检索与生成的耗时、上下文规模、本体扩展出的知识点，以及每个分块的得分明细
（在两条通道中的排名与融合得分）。这是为了让排序依据可解释。

**Q：你们用的哪个大模型？为什么选它？**
A：DeepSeek 的 `deepseek-flash`，通过 OpenAI 兼容接口调用。
选它的原因是它提供 OpenAI 兼容协议，因此后端代码不绑定任何特定厂商 —— 把 `base-url` 和 `model` 换掉就能切到通义千问、智谱、Moonshot 或本地 Ollama。
换成本的只是一个配置文件里的两行。

**Q：max-tokens 为什么设成 16000 这么大？**
A：因为 `deepseek-flash` 是推理类模型，思考过程与答案共同占用这个额度，而思考长度是随机的（同一问题实测在 500~4000 tokens 之间浮动）。设小了会偶尔出现「只想了没答」——content 为空、finish_reason=length，系统随即降级为离线抽取式。max-tokens 是**上限而非预留**，按实际用量计费，所以留大不会额外花钱，只是给随机性留出余量。

**Q：如果大模型的 API 调用失败或者超时怎么办？**
A：`ChatService.tryComplete()` 会返回 null，`RagService` 转而使用离线抽取式回答，
并在界面上明确标注"当前为离线抽取式回答"。用户不会看到空白或报错。

**Q：你们怎么防止大模型编造引用？**
A：来源编号是系统在组装上下文时赋予的，模型只能引用已存在的编号；
前端渲染引用时以系统保存的 `citations` 数组为准，
即使模型文本中的编号写错，也点不到不存在的来源。

**Q：164 个分块是怎么算出来的？**
A：60 条知识条目的正文加上附件抽取出的文本，按 420 字符分块并加 80 字符重叠后，
共产生 164 个分块。这是系统首次启动时自动构建的，日志中有记录。

**Q：如果知识量增长一百倍，你的设计还成立吗？**
A：检索部分需要改。暴力比对在百万级分块下不可行，需要引入 ANN 索引（如 HNSW）；
关键字通道仍然是 MySQL 全文索引，性能可以接受；
分块与向量化的耗时也会线性增长，届时需要改为增量索引而不是全量重建。
