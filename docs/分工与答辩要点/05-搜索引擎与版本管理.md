## 三、必须掌握的知识点

### 3.1 倒排索引：正排 vs 倒排

**是什么** —— 正排索引是「文档 → 内容」，扫描时逐篇读正文判断是否包含查询词，复杂度随文档数线性增长。倒排索引是「词项 → 文档列表」，建立一次词项到文档 id 集合的映射（posting list），查询时只需取出查询词对应的列表再做交集，无需扫描全部文档，因此检索快。

**本系统怎么用的** —— `kb_item` 上建立全文索引 `ft_item_ngram (title, summary, plain_text) WITH PARSER ngram`，底层即 InnoDB 维护的倒排索引；`SearchService.tryFulltext` 通过 `MATCH(...) AGAINST(:kw IN NATURAL LANGUAGE MODE)` 走这条索引召回。

**为什么这么做** —— 知识库是全库检索场景，正排扫描在数百条时勉强可用，但查询词命中分布广时开销不可控；倒排把「找哪些文档含这个词」变成一次索引查找。失效条件：短字段、全表极小的场景倒排收益有限；本系统数据规模在万级以内，MySQL 完全胜任。

**可能被追问**：倒排索引的 posting list 里存什么？—— 存词项对应的文档 id 集合，MySQL 还额外维护词频与位置信息（ngram 场景下用于相关度计算），排序时靠这些统计量算分。

### 3.2 中文无词边界与 ngram 二元切分

**是什么** —— 英文单词以空格分隔，分词天然成立；中文句子字与字之间没有分隔符，「软件测试」到底是「软件 / 测试」还是「软件测试」需要靠算法判断。MySQL 内置全文解析器按空格与标点切词，对中文几乎无效，因此必须换解析器。`ngram` 解析器把连续文本按固定长度滑动切分为若干 n 元组（token），`ngram_token_size = 2` 即切成「二元组」。

**本系统怎么用的** —— `ngram_token_size = 2`；「软件测试」进索引时被切成 `软件 / 件测 / 测试` 三个二元 token，查询串「测试」切开后与文档中的 `测试` token 精确对上，因此命中。这是「软件测试」与「测试」都能召回的原因。查询侧 `TextUtils.queryTerms` 也会为中文查询补上字符二元组，使应用层打分与数据库索引口径一致。

**为什么这么做** —— ngram 是「用切分粒度换取召回」的方案：不需要装载中文词典，用固定的二元切分覆盖所有长度为 2 及以上的中文片段。

**已知限制（必答）**：**单字查询不会命中**。因为最小词项长度为 2，单个汉字「测」不构成任何 token，查不到「测试」。系统在无结果建议中明确提示「中文全文检索按二元切分建索引，单字查询建议改为双字及以上」，属于已知限制而非缺陷。

**可能被追问**：为什么不用 jieba 等分词器建索引？—— MySQL 全文索引的解析器运行在数据库进程内，无法直接调用 Java 分词器；若在应用层分词后写入派生字段，则引入「业务侧与索引侧词典不一致」的维护成本。ngram 用固定二元切分避开词典问题，是规模的折中。

### 3.3 TF-IDF / BM25 与 MySQL 全文相关度的局限

**是什么** —— TF-IDF 的核心是「词频 × 逆文档频率」：一个词在本篇出现越多越重要（TF），在全集越罕见越有区分度（IDF）。BM25 在此之上加入文档长度归一化与饱和函数。MySQL `MATCH ... AGAINST` 的相关度就是一个 TF-IDF 变体。

**本系统怎么用的** —— 数据库返回的相关度在 `SearchService.buildHits` 中按下式归一化后作为一路信号：`fulltextScore = min(raw / maxScore, 1.0)`，再乘权重 0.25。它不做主导，只保证正文里的深入匹配也能被体现。

**为什么这么做** —— 直接拿数据库相关度排序会出问题：ngram 场景下，长文档天然包含更多二元 token，被记录词频推高，相关度虚高。局限正是「**偏好长文档、缺乏字段区分**」——它不知道「标题命中」比「正文出现」重要得多。因此它只能当一路输入，不能当排序依据。

**可能被追问**：BM25 里的 k1、b 参数起什么作用？—— k1 控制词频饱和速度（避免同一词堆叠无限加分），b 控制文档长度归一化强度；MySQL 未把这两个参数开放给用户，这也是它不如专用检索引擎可控的一点。

### 3.4 为什么数据库只负责召回、排序交给应用层

**是什么** —— 把「找哪些文档可能相关」（召回）与「把它们按相关程度排好」（排序）拆成两个阶段。数据库只出候选集，最终顺序由应用层打分决定。

**本系统怎么用的** —— `tryFulltext` 并不直接 `LIMIT size`，而是先放大候选：`fetchSize = min(max((page + 1) * size * OVERSAMPLE, size), MAX_CANDIDATES)`，`OVERSAMPLE = 6`、`MAX_CANDIDATES = 300`。数据库按自身相关度返回这 300 条以内的候选 id 与得分，应用层 `buildHits` 重新打分排序后，再在内存里做本地分页（`hits.subList(from, to)`）。

**为什么这么做** —— 这是缺陷②的直接修复。若按数据库相关度直接取前 10 条，标题精确命中的长报告根本进不了候选池，之后再怎么重排也无济于事。放大 6 倍是为了给应用层留出「把真正相关的挑上来」的空间，300 条上限则防止深翻页时一次加载过多记录。失效条件：候选池再大也容纳不下的极端情况（查询词与标题毫无重叠、正文命中极靠后），此时只能靠用户改写查询。

**可能被追问**：本地分页会不会导致深翻页时总数不准？—— 返回的 `total` 用的是数据库 `countQuery` 的真实命中总数，用于前端分页器；候选池受 300 上限约束，所以深翻页时可见结果有限，属于刻意的成本控制。

### 3.5 应用层打分：字段命中率 + 归一化

**是什么** —— 最终得分 `score = 字段命中率 × 0.65 + 全文相关度 × 0.25 + 热度 × 0.10`。字段命中率 = 标题覆盖 × 0.80 + 摘要与关键词覆盖 × 0.20；「覆盖」= 命中的查询词数 / 查询词总数（`SearchService.coverage`）。

**本系统怎么用的** —— 查询词来自 `TextUtils.queryTerms`，包含完整查询串、jieba 分词结果与中文字符二元组三部分。标题完整包含整个查询串时额外 **+0.20**，最后 `Math.min(score, 1.0)` 截断。得分与来源说明写入 `Hit.score` / `Hit.scoreDetail`，界面直接展示，答辩时可当场核对。

**为什么这么做** —— 字段命中最能代表「用户想要这个文档」，所以给最高权重 0.65，其中标题又是摘要权重的 4 倍（0.80 : 0.20）。标题整串命中再奖励 0.20，因为这类结果几乎总是用户想要的。归一化到 0~1 是为了让不同查询之间的得分可比、便于展示。

**可能被追问**：为什么标题权重是摘要的 4 倍？—— 标题是作者对文档内容的高度概括，命中标题说明文档主题与查询一致；摘要与关键词只是次级信号，且摘要可能由系统抽取、噪声更大。

### 3.6 对数压缩：避免热门文档长期霸榜

**是什么** —— 热度项写成 `popularity = min(1.0, log1p(viewCount) / log1p(500))`，用对数把浏览量压缩到 0~1。

**本系统怎么用的** —— `buildHits` 中计算，乘权重 0.10 计入总分。`log1p` 即 `ln(1+x)`，500 次浏览处恰好趋于 1.0。

**为什么这么做** —— 浏览量是重尾分布：头部文档可能是尾部文档的几百倍。若线性计入，热门文档会因为浏览量长期占据首位，新发布的优质文档永无出头之日。对数压缩让「500 次」与「5000 次」的差距从 10 倍缩到约 1.3 倍，热度退化为**同等相关度时的区分项**，而不是主导项。失效条件：数据规模与用户量增长后，500 这个基准值需要重新标定。

**可能被追问**：为什么权重只有 0.10？—— 热度反映的是「多少人看过」而非「与查询多相关」，权重过高会把检索变成热榜，与检索意图相悖，因此刻意压低。

### 3.7 弱匹配标记 `weakMatch`

**是什么** —— 当没有任何一条结果在标题或摘要（含关键词）上命中查询词时，把结果集标记为「弱匹配」，界面据此提示用户这是模糊结果。

**本系统怎么用的** —— `SearchService.search` 中判断：`hits.stream().noneMatch(h -> h.getTitleMatch() || h.getSummaryMatch())`。`titleMatch` / `summaryMatch` 由 `buildHits` 按 `coverage > 0` 写入。前端 `SearchView.vue` 用 `el-alert` 提示「未找到精确匹配的内容」。

**为什么这么做** —— 关键在于**不隐藏结果**。正文命中同样是有效召回，如果因为「标题摘要都没命中」就直接丢弃，会误伤「关键词只出现在附件正文里」的查询。正确做法是如实标记、由用户判断，而不是把弱匹配伪装成精确匹配。失效条件：仅靠标题摘要判断可能把「正文里其实讲得很透彻」的文档也标为弱匹配，所以是提示而非过滤。

**可能被追问**：弱匹配和「无结果」有什么区别？—— 无结果是 `hits` 为空，给出替代建议；弱匹配是有结果但没有精确命中，结果照常展示、只在顶部加提示。

### 3.8 降级通道：保证查询不白屏

**是什么** —— 全文索引不可用或零命中时，退回 `LIKE` 模糊匹配。

**本系统怎么用的** —— `tryFulltext` 抛异常时静默返回空候选；主流程发现候选为空即调用 `fallbackLikeSearch`：先用 `attachmentRepository.searchItemIdsByFulltext` 找附件正文命中的条目并合并，仍无结果再按标题 `contains` 兜底；打分改用 `heuristicScore`（标题 +3.0 / 摘要 +1.0 / 正文 +0.3，加少量浏览量）。此时 `modeUsed` 显示「模糊匹配（全文索引未命中，已降级）」，`fulltextUsed = false`，界面用不同颜色的标签区分。

**为什么这么做** —— 检索是系统的核心入口，白屏的体验代价远高于「结果相关性略低」。降级路径同时也是可观测的：`modeUsed` 字段让演示者能一眼看出本次走了哪条通道。

**可能被追问**：降级路径会不会拖慢响应？—— `LIKE '%kw%'` 无法走索引，但知识库规模在百级条目、且兜底查询 `limit(50)`，实测耗时可接受。

### 3.9 高级检索的动态条件构造

**是什么** —— 分类、资产类型、标签、知识点、作者、时间区间、标题限定、附件限定等条件可自由组合，条件是「与」关系，未填写的条件不参与查询。

**本系统怎么用的** —— `KnowledgeItemService.buildSpec` 返回一个 `Specification<KnowledgeItem>`，按 `List<Predicate>` 逐条 `cb.and` 拼装。单值条件直接 `cb.equal`；**多值条件不能直接 join**：标签与知识点先查关联表 `kb_item_tag` / `kb_item_concept` 取条目 id 集合（`tagLinkRepository` / `conceptLinkRepository.findItemIdsByConceptIds`），再对 `root.get("id").in(ids)` 过滤，集合为空时用 `cb.disjunction()` 表示「必然不命中」。资产类型因为就在主表，直接 `root.get("assetType").in(...)`。

**为什么这么做** —— `Specification` 让条件可以按需拼装，避免为每种组合写一个查询方法（组合数是 2 的幂级）。多值条件先查关联表再 `IN`，是因为条目与标签 / 知识点是 M:N 关系，关联表是唯一的事实来源；在 Criteria 里直接 join 多张表会让 SQL 与分页 count 都变复杂。

**可能被追问**：为什么空集合用 `cb.disjunction()` 而不是跳过条件？—— 用户选了标签但没有任何条目打这个标签时，正确语义是「没有结果」，跳过条件反而会返回全部条目，语义错误。

### 3.10 分类检索含子树

**是什么** —— 按分类筛选时，除了该分类本身的条目，还要包含其全部后代分类的条目。

**本系统怎么用的** —— `CategoryService.selfAndDescendantIds(categoryId)` 返回自身与全部后代 id；`buildSpec` 里 `root.get("categoryId").in(catIds)`，全文通道 `searchInCategoryScope` 则改用 `fulltextSearchInCategories(keyword, "", catIds, pageable)`。分类树用物化路径维护，取子树是一次前缀匹配。

**为什么这么做** —— 用户心智中「软件工程」这个父分类天然包含「需求 / 设计 / 测试」等子分类的内容，若只匹配分类 id 本身，用户会以为知识库缺内容。失效条件：分类树很深的场景下 `IN` 列表会变长，本系统分类层级有限，不构成问题。

**可能被追问**：空集合时 `searchInCategoryScope` 返回什么？—— 返回 `Page.empty(pageable)`，不发起查询，避免 `IN ()` 造成语法错误。

### 3.11 搜索联想的多来源合并

**是什么** —— 输入前缀时给出候选词，来源有三类：历史搜索词、本体知识点、知识条目标题。

**本系统怎么用的** —— `SearchService.suggest`：`searchLogRepository.findKeywordsStartingWith(kw, ...)` 取历史词（`LIKE 'kw%'` 可走 `idx_search_keyword` 索引）；`ontologyService.search(kw)` 取知识点（`type = CONCEPT`，带 `refId`）；`itemRepository.findHot` 取热门条目后按标题 `contains` 过滤（`type = TITLE`）。三类结果用 `LinkedHashMap` 按文本去重，再截断到 `limit`。空输入时直接返回热搜词作为起点。

**为什么这么做** —— 单一来源的联想覆盖不全：历史词体现「大家搜什么」，知识点体现「知识结构里有什么」，标题体现「库里实际有什么」。合并后用 `LinkedHashMap` 去重且保持「历史词优先」的相对顺序，让高频查询词排在前面。

**可能被追问**：为什么不直接在数据库里 union 三张表？—— 三类数据的匹配语义不同（前缀 / 全文 / 子串），在应用层分别取再合并更清晰，也能统一做去重与限流；接口层面 `limit` 上限 20，成本可控。

### 3.12 热搜词与零结果检索词

**是什么** —— 热搜词是窗口内出现次数最多的查询词；零结果检索词是窗口内「搜过但结果数为 0」的查询词，按次数排序。

**本系统怎么用的** —— 每次检索 `SearchService.recordSearch` 落一条日志到 `search_log`（`keyword` / `search_type` / `result_count` / `cost_ms` / `created_at`）。`SearchLogRepository.hotKeywords` 与 `noResultKeywords` 都是 `GROUP BY keyword ORDER BY count DESC`，窗口由 `props.getSearch().getHotKeywordWindowDays()` 决定，默认 **30 天**。前端 `SearchStatsView.vue` 用两张横向条形图展示，并配「近 30 天检索次数」「平均耗时」两个指标卡。

**为什么这么做** —— 热搜词反映用户关注点，是运营信号；**零结果检索词价值更高**：它直接暴露知识库的内容缺口——用户想找的东西库里没有。把零结果词做成榜单，等于给内容建设方一份带优先级的补库清单。

**可能被追问**：为什么统计窗口取 30 天？—— 太短则样本不足、榜单抖动；太长则反映不出近期热点变化。30 天是「有统计意义」与「跟得上变化」之间的折中。

### 3.13 LCS 最长公共子序列：原理与回溯

**是什么** —— LCS 求两个序列中「保持相对顺序、不要求连续」的最长公共子序列。用它做行级 diff，可以正确识别「中间插入若干行」这类改动（逐行对照做不到）。

**本系统怎么用的** —— `DiffService.computeLineDiff` 先建长度表 `lcs[i][j]`，递推：两行相等取 `lcs[i+1][j+1] + 1`，否则取 `max(lcs[i+1][j], lcs[i][j+1])`；再从左上角 `(0,0)` 回溯——相等则输出 `SAME` 并双双前进，否则比较右邻与下邻，`lcs[i+1][j] >= lcs[i][j+1]` 时把旧行标 `REMOVE`（说明旧行的内容在后面还能配上），否则把新行标 `ADD`。末尾残余行分别补 `REMOVE` / `ADD`。复杂度 **O(n·m)** 时间、O(n·m) 空间。

**为什么这么做** —— 行级 diff 用整行相等做判据，天然适合 LCS；相比「逐行比较 + 偏移量」的朴素做法，LCS 能正确区分「插入」与「替换」。失效条件：`MAX_LINES = 3000`，任一侧超过 3000 行就退化为「整体替换」（旧行全标 `REMOVE`、新行全标 `ADD`），避免 O(n·m) 在超大文档上耗时过长。

**可能被追问**：为什么回溯时比较 `lcs[i+1][j] >= lcs[i][j+1]` 而不是反过来？—— 这个取向决定并列时优先输出删除还是插入；取「先删后加」更符合阅读习惯，且与常见 diff 工具的输出一致。

### 3.14 上下文折叠的必要性

**是什么** —— 差异结果里，只保留改动行前后各 3 行上下文，其余大段未改动内容折叠为一条占位行 `SKIP`。

**本系统怎么用的** —— `DiffService.collapseContext`：先标记所有改动行 ±3 行为 `keep`，再顺序遍历，未被 `keep` 的连续区间合并成一条 `DiffLine.of("SKIP", null, null, "⋯ 未改动的上下文已折叠 ⋯")`。`contextSize = 3` 是硬编码。前端 `VersionHistoryView.vue` 对 `type === 'SKIP'` 的行渲染为 `.is-skip` 样式。

**为什么这么做** —— 两个版本之间往往只改动几行，如果原样返回全部正文，前端要渲染上千行相同内容，既卡顿又让真正的改动淹没在噪声里。折叠后差异面板聚焦在改动处。失效条件：用户确实想看全量对比时无法展开——这是当前实现的取舍。

**可能被追问**：为什么上下文取 3 行？—— 3 行足以看懂改动所处的段落语境（一个 Markdown 段落或列表项），再多则折叠效果不明显，属于经验值。

### 3.15 全量快照 vs 增量补丁

**是什么** —— 保存版本时有两种策略：全量快照把该时刻的完整内容原样存一份；增量补丁只存相对上一版的差异（patch），还原时按顺序重放。

**本系统怎么用的** —— `cms_item_version` 存的是**全量快照**：`title` / `summary` / `content` / `category_id` / `asset_type` 全部完整落库，另加 `concepts_snapshot`（形如 `12:软件测试|15:单元测试`）与 `tags_snapshot`。`content_hash` 存正文 MD5，用于判断内容是否真的变化。

**为什么这么做** —— 全量快照的代价是存储，收益是**读路径极简**：查看任意版本、回滚、比对都只需取出这一行，不用重放历史。增量方案每次查看都要从头重算，任何一环损坏则后续版本全部不可读。课程设计的数据规模下存储完全不是瓶颈，因此选全量。失效条件：内容量极大且版本极密时（如系统日志）全量会浪费存储，那时才需要增量或压缩。快照里存概念**名称**而非仅 id，是为了概念被重命名后历史版本仍能还原「当时标注了什么」，让版本记录自解释。

**可能被追问**：`content_hash` 有什么用？—— `doSnapshot` 里若新正文的 MD5 与上一版本相同（且来源不是 PUBLISH），则跳过建版，避免用户打开编辑器又原样保存时刷出一堆无意义的空版本。

### 3.16 双阈值建版策略

**是什么** —— 是否为条目建立新版本，由两个阈值共同判定：距上次快照的天数 ≥ `intervalDays`，或自上次快照以来累计修改次数 ≥ `minChangeCount`。两个条件是**「或」**关系，满足其一即建版。系统默认 `intervalDays = 1` 天、`minChangeCount = 5` 次。

**本系统怎么用的** —— `VersionPolicyService.evaluate` 计算 `byDays` 与 `byCount` 并返回 `SnapshotDecisionDTO`（含 `due`、`reason`、`daysSinceLastSnapshot`、`pendingChangeCount`），`reason` 会明确写出「是时间先到还是改动量先到」。天数基准取 `last_snapshot_at`，为空则回退 `created_at`；`pendingChangeCount` 取 `kb_item.change_count`，它在条目每次保存（`KnowledgeItemService` 第 121 行）与发布（第 175 行）时 +1，快照生成后由 `VersionService.doSnapshot` 重置为 0。

**为什么这么做** —— 这是本题「指定天数 / 修改次数」要求的核心。单用天数阈值：当天改十次也只留一个版本，密集修改之间的中间状态全部丢失；单用次数阈值：低频文档可能几个月都不建一版，时间维度上没有回溯点。**取「或」** 意味着无论从「时间跨度」还是「修改密度」哪个角度看，都能保证存在足够密的历史回溯点。失效条件：两个阈值都设得过小（如 0 天 / 1 次）会退化为每次保存都建版，需要靠 `max_versions` 淘汰兜住。

**可能被追问**：天数阈值用 `>=` 还是 `>`？—— 用 `>=`：`days >= intervalDays`，即「恰好等于阈值」也建版，测试报告里 1 天阈值在 1 天时建版、2 天也建版可佐证。

### 3.17 三级策略作用域与优先级

**是什么** —— 版本策略分三层：条目级（`ITEM`）、分类级（`CATEGORY`）、全局级（`GLOBAL`）。

**本系统怎么用的** —— `VersionPolicyService.resolve(itemId, categoryId)` 的解析顺序是 **ITEM → CATEGORY → GLOBAL，命中即停止**：先查该条目是否有启用的条目级策略，有就返回；否则查其分类级；再否则查全局级；全都没有则用 `fallbackPolicy()` 的代码内置默认值（1 天 / 5 次 / 50 个）。每层内部按 `priority` 降序取第一条（`findByScopeAndScopeIdAndEnabledOrderByPriorityDesc`，只取 `enabled = 1`）。全局策略至少保留一条，否则删除接口拒绝（`delete` 方法）。

**为什么这么做** —— 分层让「默认规则 + 例外覆盖」成为可能：全局定基准，敏感分类（如规范文档）可以单独配更严的策略，个别条目还能再覆盖。`priority` 只在同一作用域内生效，避免跨层排序带来的语义混乱。失效条件：`scope_id` 指向的分类 / 条目被删除后策略变成悬空配置，`resolveTargetName` 会显示为「分类#id」以便管理员发现。

**可能被追问**：如果条目级策略把 `autoSnapshot` 关了会怎样？—— `evaluate` 直接返回 `due = false`，并说明「自动快照已关闭，仅在手工创建 / 发布时生成版本」，发布仍会无条件建版（`snapshot(item, SOURCE_PUBLISH, ...)`）。

### 3.18 回滚必须留痕

**是什么** —— 回滚到历史版本时，不是「删除后续版本、把内容退回去」，而是产生一条新的版本记录。

**本系统怎么用的** —— `VersionService.rollback` 分三步：①先 `doSnapshot(item, SOURCE_MANUAL, "回滚至 vN 前的自动留存", ...)` 把**当前状态**存一份，防止回滚动作本身造成内容丢失；②把目标版本的 `title` / `summary` / `content` / `categoryId` / `assetType` 写回条目，`changeCount` +1；③`snapshot(item, SOURCE_ROLLBACK, log)` 生成内容与目标版本一致但 `changeSource = ROLLBACK` 的**新版本**。随后写审计日志并发布 `ItemChangedEvent.rolledBack(itemId)` 通知 RAG 重建索引。目标版本已是当前版本时直接拒绝。

**为什么这么做** —— 版本链只增不减，任何一次操作都可追溯：回滚本身也是一次变更，应该被记录，否则「谁在什么时候回滚到哪一版」就查不到了。同时留存回滚前的状态，用户发现回滚错了还能回到回滚前。失效条件：无——这是刻意不提供的「破坏性回滚」，牺牲了存储换取可追溯性。

**可能被追问**：回滚后版本号和内容是什么关系？—— 回滚生成的 `vN+1` 内容等于 `vM`（目标版本），即版本号在推进，内容在「倒退」，两者不必单调一致，这正是版本链完整性的体现。

### 3.19 版本淘汰

**是什么** —— 每个条目保留的版本数有上限 `max_versions`（默认 50），超出后删除最旧的版本。

**本系统怎么用的** —— `doSnapshot` 末尾调用 `pruneIfNeeded(itemId, policy.getMaxVersions())`；`pruneIfNeeded` 先 `countByItemId`，超过 `keep`（`maxVersions` 为空或不大于 0 时按 50）才执行 `pruneOldVersions(itemId, keep)`。另有 `pruneAll()` 供管理员手工全量清理，对应前端「全量清理」按钮。

**为什么这么做** —— 无条件建版 + 全量快照的组合会让存储随编辑次数线性增长，必须有回收机制。淘汰「最旧」而非「最不活跃」是因为版本的价值随时间递减，且「最旧」的判定无需额外统计。失效条件：如果条目需要永久保留全部历史（如合规审计场景），应把 `max_versions` 调大或关闭清理——本系统通过策略字段把控制权交给管理员。

**可能被追问**：为什么不按时间淘汰而按条数？—— 条数上限对存储的控制更直接、可预测；时间维度已经由天数阈值在建版侧控制密度，两者分工不重叠。

## 四、答辩预设问答

**Q：为什么用 MySQL 全文索引而不是 Elasticsearch？**
A：数据规模在万级，MySQL 完全胜任；索引与业务数据同库同事务，不存在主库与索引不一致的时间窗口；省去部署中间件的成本，对两周的课程设计是负收益。失效边界明确：数据量增长到百万级就应换专用检索组件。

**Q：ngram 二元切分的原理是什么？为什么查单个汉字没结果？**
A：ngram 解析器把文本按固定长度滑动切成 n 元组，`ngram_token_size = 2`，「软件测试」切成 `软件 / 件测 / 测试`。最小词项长度是 2，单个汉字不构成词项，所以查「测」不会命中「测试」——这是已知限制，系统在无结果建议里明确提示改用双字及以上。

**Q：检索时的得分公式是什么？**
A：`字段命中率 × 0.65 + 全文相关度 × 0.25 + 热度 × 0.10`。字段命中率 = 标题覆盖 × 0.80 + 摘要与关键词覆盖 × 0.20；标题完整包含整个查询串时额外 +0.20，总分截断到 1.0。界面上 `scoreDetail` 会显示每一项的实际数值。

**Q：`OVERSAMPLE = 6` 和 `MAX_CANDIDATES = 300` 是干什么的？**
A：全文通道不直接 `LIMIT size`，而是按页深放大候选集：`fetchSize = min(max((page+1) * size * 6, size), 300)`。放大是为了给应用层重排留出空间，300 条上限防止深翻页一次加载过多记录。

**Q：为什么数据库只召回、排序交给应用层？**
A：ngram 相关度偏好长文档（长文包含更多二元组、词频更高），直接按它取前 10 条，会让标题精确命中的文档根本进不了候选池，应用层再重排也没用。这是测试报告缺陷②的修复方案：先多召回、再按字段命中率重排。

**Q：热度项为什么要取对数？**
A：`popularity = min(1, log1p(浏览量) / log1p(500))`。浏览量是重尾分布，线性计入会让热门文档长期霸榜、新文档永无出头之日。对数把 500 与 5000 次的差距从 10 倍压到约 1.3 倍，让它退化为同等相关度时的区分项。

**Q：`weakMatch` 是什么？会不会把结果藏起来？**
A：当没有任何结果在标题或摘要（含关键词）上命中查询词时置位，界面提示「未找到精确匹配的内容」。**不隐藏结果**——正文命中也是有效召回，直接丢弃会误伤「关键词只出现在正文」的查询，所以选择如实标记。

**Q：全文索引查不到时会白屏吗？**
A：不会。`tryFulltext` 异常或零命中时自动降级到 `fallbackLikeSearch`：先合并附件正文命中的条目，再按标题 `contains` 兜底，用 `heuristicScore` 自行打分。`modeUsed` 字段会显示「模糊匹配（全文索引未命中，已降级）」。

**Q：高级检索的多个条件是「与」还是「或」？怎么实现的？**
A：「与」关系。`KnowledgeItemService.buildSpec` 用 `Specification` 把每个条件拼成一个 `Predicate` 再 `cb.and`。标签、知识点这类多值条件先查关联表 `kb_item_tag` / `kb_item_concept` 取条目 id，再对 `id IN (...)` 过滤；集合为空时用 `cb.disjunction()` 表示必然不命中。

**Q：按父分类检索，子分类的内容会出来吗？**
A：会。`CategoryService.selfAndDescendantIds` 返回自身与全部后代分类 id，全文通道用 `fulltextSearchInCategories`，条件通道用 `categoryId IN (...)`。

**Q：搜索联想的结果是哪来的？怎么去重？**
A：三个来源——历史搜索词（`search_log` 前缀匹配，走 `idx_search_keyword`）、本体知识点（`ontologyService.search`）、热门条目标题（`findHot` 后子串过滤）。用 `LinkedHashMap` 按文本去重，保持「历史词优先」顺序，截断到 limit。

**Q：零结果检索词有什么用？**
A：它是知识库内容缺口的直接证据——用户搜过但库里没有。做成榜单等于给内容建设一份带优先级的补库清单，比热搜词的运营价值更高。统计窗口 30 天。

**Q：版本什么时候建？两个阈值是「与」还是「或」？**
A：距上次快照天数 ≥ `intervalDays` **或** 累计修改次数 ≥ `minChangeCount`，满足其一即建版，默认 1 天 / 5 次。用「或」是因为：只用天数，当天改十次只留一版，中间状态丢失；只用次数，低频文档几个月不建版，时间上无回溯点。取「或」在两个维度都保证有回溯点。

**Q：三级策略是怎么解析的？**
A：`VersionPolicyService.resolve` 按 **条目级 → 分类级 → 全局级** 顺序找启用策略，命中即停止；都没有则用代码内置默认。每层内部按 `priority` 降序取第一条。全局策略至少保留一条，删到只剩一条时接口会拒绝。

**Q：为什么版本用全量快照而不是增量补丁？**
A：全量快照的读路径极简——查看、比对、回滚都只需取一行，不用重放历史；增量方案任一环损坏则后续版本全不可读。课程设计的数据规模下存储不是瓶颈，因此选全量。若内容量极大且版本极密则需要增量或压缩。

**Q：`content_hash` 字段是做什么的？**
A：存正文 MD5。`doSnapshot` 里若新正文 MD5 与上一版本相同（来源不是 PUBLISH），则跳过建版，避免用户打开编辑器又原样保存时刷出无意义的空版本。

**Q：回滚会不会删掉后面的版本？**
A：不会。回滚分三步：先为**当前状态**留一份快照（防止回滚本身造成丢失），再把目标版本内容写回条目，然后生成一条 `changeSource = ROLLBACK` 的新版本。版本链只增不减，每次操作都可追溯；回滚后还会发布事件通知 RAG 重建索引。

**Q：版本数会不会无限增长？**
A：不会。`pruneIfNeeded` 在每次建版后检查，超过 `max_versions`（默认 50）就淘汰最旧的版本；管理员也可在版本策略页手工触发全量清理（`pruneAll`）。
