## 三、必须掌握的知识点

### 1. 物化路径表达树形结构
**是什么** —— 物化路径（materialized path）在每个节点上保存一条从根到自身的完整路径字符串，如 `/1/4/9/`。配合邻接表 `parent_id`，构成"邻接表 + 物化路径"双表示。
**本系统怎么用的** —— `kb_category` 与 `ont_concept` 都有 `parent_id`、`level`、`path` 三列。建根节点时 `path = "/" + id + "/"`，建子节点时 `path = 父.path + id + "/"`（见 `CategoryService.create`）。取某节点整棵子树用 `CategoryRepository.findSubtree`，JPQL 为 `path like concat(:path, '%')`。
**为什么这么做** —— 只要一次索引前缀匹配就能取出整棵子树，无需递归。**为什么不用递归查询（WITH RECURSIVE）**：递归 CTE 在每一层都要再查一次，且 MySQL 对递归深度有 `cte_max_recursion_depth` 限制，写法与性能都更复杂。物化路径是"以空间换查询效率"。**失效条件**：节点被移动时，其所有后代的 `path` 都要重写，写入代价随子树规模上升；若树频繁大规模移动，物化路径会吃亏。
**可能被追问**：`path` 和 `parent_id` 重复吗？——不重复。`parent_id` 管维护与单层查询，`path` 管子树查询，两者分工不同。

### 2. 移动节点时维护路径与防环
**是什么** —— 改变节点的父节点时，必须重写自身与全部后代的 `path` 和 `level`。防环即禁止把节点移到自己或自己的后代之下。
**本系统怎么用的** —— `CategoryService.update`：先判 `req.parentId == id`（父不能是自身），再判 `newParent.path.startsWith(c.path)`（新父在自己的子树里，会成环），命中即抛 `不能把分类移动到自己的子分类下，会产生环`。确认无环后重算自身 `path`/`level`，再递归 `refreshDescendants` 刷新所有后代。
**为什么这么做** —— 环会让树变成图，`findSubtree` 的前缀匹配将无限递归且永远取不完。递归重写后代是物化路径的固有代价，用一次写换后续所有读。
**可能被追问**：不用递归能重写后代路径吗？——可以，用 `findSubtree(oldPath)` 一次取出后代再逐个替换前缀即可；本系统选择了递归写法，逻辑更直观。

### 3. M:N 联系的建表方式
**是什么** —— M:N 联系必须单独建关联表，主码为两端主码的组合。
**本系统怎么用的** —— `kb_item_tag(item_id, tag_id)` 复合主键，另有 `idx_it_tag(tag_id)` 支持按标签反查；`kb_item_concept(item_id, concept_id, source, confidence)`，`source` 取 `MANUAL`/`AUTO`，`confidence` 为 `DECIMAL(4,2)`。对应实体 `ItemTagLink`、`ItemConceptLink` 用 JPA 的 `@IdClass` 声明复合主键。
**为什么这么做** —— 关联表能把"关系"本身当数据存，从而携带联系属性（谁是手工标的、置信度多少）。若用 `kb_item.tags = 'a,b,c'` 逗号串，则违反 1NF，无法建外键、无法按标签索引、无法记录置信度。**失效条件**：关联表在超大规模下会成为热点写入点，但本系统 60 条条目的规模完全不构成问题。
**可能被追问**：为什么 `kb_item_concept` 不叫 `kb_item_ontology`？——命名与概念表 `ont_concept` 的模块前缀保持一致，`kb_` 前缀表示它归属知识库侧的标注关系。

### 4. 内容状态机与流转合法性校验
**是什么** —— 状态机是有限状态的集合加上允许的迁移。非法迁移必须被拒绝。
**本系统怎么用的** —— 四态：`DRAFT`（草稿）、`PENDING`（待审）、`PUBLISHED`（已发布）、`ARCHIVED`（已归档），常量定义在 `KnowledgeItem`。迁移：`submit` 只允许 `DRAFT→PENDING`；`publish` 禁止对 `PUBLISHED`/`ARCHIVED` 再发布，且要求**有正文或有附件**（`!hasText(content) && attachmentRepository.countByItemId(id)==0` 时报错）；`unpublish` 只允许 `PUBLISHED→DRAFT`；`archive` 任意非归档态→`ARCHIVED`；`unarchive` 只允许 `ARCHIVED→DRAFT`（**故意回草稿而非直接发布**，让人重新确认内容是否过时）。已归档条目在 `update` 中被拒绝编辑。
**为什么这么做** —— 每个迁移前置校验把非法调用挡在业务层，避免出现"已归档又被发布"这类脏状态。恢复回草稿而不是直接发布，是因为归档往往意味着内容已过时。**失效条件**：本系统没有独立审核角色，`publish` 不校验当前用户是否为审核人，严格流程下需补充。
**可能被追问**：只有 `PUBLISHED` 进入公开检索吗？——是。列表接口在 `includeUnpublished=false` 时强制 `status='PUBLISHED'`，RAG 召回也只取已发布内容。

### 5. 中文分词与关键词抽取
**是什么** —— 中文没有词边界，需先分词。jieba 是常用的中文分词器，有"精确模式"与"搜索引擎模式"等。
**本系统怎么用的** —— `TextUtils` 持有单例 `JiebaSegmenter`，`tokenize` 用 `SegMode.SEARCH`（搜索引擎模式，长词会额外切出短词以提高召回），随后过滤停用词、过滤单字非中文、过滤纯标点。另内置一份约 90 词的 `DOMAIN_WORDS` 领域词典（"需求获取""等价类划分""物化路径"等），避免术语被切碎。
**为什么这么做** —— 搜索引擎模式兼顾精度与召回；领域词典因为通用词典不认识软件工程与数据库术语。分词结果用于三处：关键词抽取、检索高亮、自动概念标注。**失效条件**：jieba 词表未覆盖的新术语仍会被切错，只能靠持续补充 `DOMAIN_WORDS` 缓解；单字查询（长度 1）会被过滤掉。
**可能被追问**：分词和 MySQL 的 ngram 是一回事吗？——不是。分词在 Java 应用层做关键词与高亮，ngram 是数据库按二元切分建全文索引，两者是并行的两套口径。

### 6. TF 加权的关键词打分公式
**是什么** —— 抽取关键词的常用做法是按词频（TF）打分取 Top-N，本系统在此之上叠加长度、标题命中与领域词加权。
**本系统怎么用的** —— `TextUtils.extractKeywords(text, title, 8)`，打分函数 `score` 为：
`(词频 + 长度加权 + 标题加权 + 领域词加权) × 类型惩罚`，其中**长度加权** = `min(词长,6) × 0.35`，**标题加权** = 命中标题记 `1.5`，**领域词加权** = 属于 `DOMAIN_WORD_SET` 记 `2.0`，**类型惩罚** = 纯数字 `×0.3`。条目保存时取 Top 8 写入 `kb_item.keywords`（逗号分隔）。
**为什么这么做** —— 纯词频会选出"系统""数据"这类高频但无区分度的词；领域词加权让专业术语浮上来，标题命中说明它更可能是主题词，长度加权倾向更具体的长词。**失效条件**：这是启发式打分，没有 IDF 项，因此对"高频但到处都出现的领域词"仍可能误选；要做真正的最优需引入 TF-IDF 或 TextRank。
**可能被追问**：为什么给领域词加 2.0 而不是乘一个比例？——加性偏置与长度、标题项同量级，便于调参；若改成乘性权重会让长领域词分数过度膨胀。

### 7. 本体概念的自动标注
**是什么** —— 自动标注是把条目正文里出现的知识点识别出来，挂到 `kb_item_concept` 上。
**本系统怎么用的** —— `replaceConcepts` 先清空该条目的旧标注，再写入手工指定的概念（`source=MANUAL`、`confidence=1.0`），随后若 `autoTagConcepts` 为真，用 `title + plain_text` 调用 `ontologyService.link(text, 15)`，结果以 `source=AUTO`、`confidence=0.7` 写入；手工与自动命中同一概念时以手工为准（`putIfAbsent`）。
**长词优先词典扫描的思路** —— `OntologyService.link` 把每个概念的**名称与别名**构成词典，按**词长倒序**排序后扫描文本。这样"需求分析"会先于"需求"被匹配，避免短词抢占长词。命中后按上述置信度落库。
**为什么这么做** —— 词典匹配可解释、零训练成本，适合术语边界清晰的课程领域；长词优先是解决"短词吞掉长词"的关键。**失效条件**：只能识别词典中已有的名称/别名，长尾概念召回有限；也无法处理否定与语境（如"这不是需求分析"）。
**可能被追问**：自动标注错了怎么办？——界面支持人工复核，手工标注优先级最高且始终保留，自动标注只在无手工时补位。

### 8. 展示用冗余计数的维护
**是什么** —— `kb_category.item_count`（分类下条目数）与 `kb_tag.use_count`（标签使用次数）是为列表展示准备的冗余计数。
**本系统怎么用的** —— 标签：`KnowledgeItemService.replaceTags` 在写完关联后用 `ItemTagLinkRepository.countGroupByTag()` 重算全部标签的 `use_count`（注释写"比增量维护更不容易漂移"）。分类：`KnowledgeItemService.adjustCategoryCount()` 在**新建、删除、改分类**三条路径上调用 `CategoryRepository.addItemCount()` 做增量调整；另有全量重算 `recalculateItemCounts()`，入口是 `CategoryService.recalculateCounts()`，并在演示数据导入结束时统一调用。前端分类树与标签云直接读这两个字段。
**为什么这么做** —— 分类树每级、标签云每次渲染都实时 `COUNT` 代价高，冗余字段把成本移到写路径。
**这里要如实说一个踩过的坑**：增量调整最初**漏接在条目保存路径上**——`addItemCount` 方法早已定义却从未被调用，导致新建条目后分类树的数字不更新，只能靠管理员手动触发全量重算。写代码时"方法存在"很容易被误当成"逻辑已实现"。发现方式是对照测试：写脚本对比"创建条目前后分类树显示的条目数"，数字没变才暴露出来。修复后新建 +1、删除 −1、改分类时旧减新增三条路径均已验证。
**可能被追问**：冗余计数怎么保证不漂移？——三个措施：把增量调整放在所有会改变计数的路径上；保持计数口径与全量重算一致（只统计未逻辑删除的条目，与草稿/已发布无关，因此归档与发布这些状态流转不需要调整计数）；保留全量重算入口作为兜底。
**另一个可能被追问**：为什么标签每次保存都重算、分类却用增量？——标签重算是一次 `GROUP BY`，成本低且能顺带清理孤立标签；分类树重算涉及全表关联，用增量更合适，全量重算只放在管理员入口与数据导入结束时。

### 9. Specification 动态查询与多值条件
**是什么** —— Spring Data JPA 的 `Specification` 用 Criteria API 在运行时拼装 `WHERE` 条件，适合"任意组合的筛选"。
**本系统怎么用的** —— `buildSpec` 恒定加 `deleted=0`；按可见性加 `status` 条件；关键词用 `title/summary/keywords` 的 `LIKE`；分类条件先用 `categoryService.selfAndDescendantIds` 取子树 id 再 `IN`；`assetTypes` 直接 `IN`；标签与概念是**多值条件**——先用 `ItemTagLinkRepository.findItemIdsByTagIds` / `ItemConceptLinkRepository.findItemIdsByConceptIds` 查出候选条目 id，再 `root.get("id").in(ids)`。
**为什么这么做** —— 标签/概念存在关联表里，如果直接 join 会破坏分页（一条记录可能匹配多行）。"先在关联表里求交集、再对主表做 IN"避免了复杂 join 分页，也让 `Specification` 保持单一主表。**失效条件**：候选 id 集可能很大（本系统 60 条无所谓），百万级时 `IN` 列表会膨胀，应改为 `EXISTS` 子查询或 join。
**可能被追问**：多值条件是"任意命中"还是"全部命中"？——本系统的语义是任意命中（`IN`），需求文档写的是"标签 id 多选（任意命中）"。

### 10. 分页与排序
**是什么** —— 分页把结果切成固定大小的页，排序决定页内顺序。
**本系统怎么用的** —— `findItems` 用 `PageRequest.of(max(page-1,0), min(max(size,1),100), sort)`，即**页码下限 1、页大小钳制在 1~100**。排序字段走白名单：`createdAt`/`viewCount`/`likeCount`/`publishedAt`/`title`/`updatedAt`，非法值回落到 `updatedAt`；方向由 `sortDir` 决定。结果封装为 `PageResult`（含 `list`、`total` 等）。
**为什么这么做** —— 钳制页大小防止一次拉全表；排序白名单防止前端传入任意列名（既是安全考虑也避免对无索引列排序）。**失效条件**：对 `title` 排序在中文下按排序规则比较，与用户直觉的拼音序不完全一致。
**可能被追问**：为什么分页上限是 100？——`AppProperties.Search.maxPageSize = 100`，与检索共用同一约定。

### 11. 软删除
**是什么** —— 软删除不物理删除行，而是置一个标志位，读时过滤。
**本系统怎么用的** —— `kb_item.deleted`（`TINYINT`，默认 0）。`delete` 只把 `deleted` 置 1；所有查询在 `buildSpec` 里恒定 `cb.equal(root.get("deleted"), 0)`；`require(id)` 在取到已删除记录时抛 `notFound`。删除时同时发布 `ItemChangedEvent.deleted` 让检索侧清理。
**为什么这么做** —— 知识条目挂有版本快照、检索分块与审计记录，物理删除会级联毁掉这些可追溯数据。软删除保留历史，也满足"删除后历史版本仍在数据库中"的界面提示。**失效条件**：软删除的记录会一直占用存储，需要定期归档或离线清理；且唯一约束（如标题）若存在会与软删除冲突——本系统标题无唯一约束，故无此问题。
**可能被追问**：软删除后计数还准吗？——计数查询统一带 `deleted=0` 条件，因此是准的。

### 12. N+1 问题与批量装配
**是什么** —— N+1 指查出 N 条主记录后，又为每条各发一次查询取关联数据，总共 N+1 次查询。
**本系统怎么用的** —— `enrichAll` 接收一批条目，用 `findAllById` / `findByItemIdIn` **一次性**把分类、作者、标签、概念、附件按 id 集合查出来，在内存里按 `item_id` 分组再分发到各 DTO。
**为什么这么做** —— 列表页一页 12 条，若每条都查 5 类关联就是 60 次查询；批量装配把它压到 5 次。**失效条件**：内存分发要求一次性载入，若单页条目极多会占用较多内存，需配合分页上限。
**可能被追问**：`enrichList` 和 `enrich` 什么关系？——`enrich` 是单条的便捷包装，内部复用 `enrichAll`；搜索引擎拿到实体列表后调用 `enrichList` 复用同一套装配。

### 13. 关联的"替换"语义
**是什么** —— 编辑条目时，标签与概念整体替换而非逐条增删。
**本系统怎么用的** —— `replaceTags`/`replaceConcepts` 都是"先 `deleteByItemId` 清空，再写入本次提交的集合"。标签按名称查 `findByName`，不存在则新建 `Tag`；概念去重后按 `MANUAL`/`AUTO` 分别写入。
**为什么这么做** —— 前端表单提交的是完整的标签/概念列表，整体替换让"取消一个标签"与"新增一个标签"用同一条路径表达，逻辑简单不易错。**失效条件**：高并发下"先删后插"在事务内是原子的（方法有 `@Transactional`），但若两个请求同时改同一条目的标签，后者会覆盖前者——本系统没有乐观锁，课程设计场景可接受。
**可能被追问**：清空再写入会不会产生大量 DELETE？——会，但关联表行数少，且都在同一事务内，代价可忽略。

## 四、答辩预设问答

**Q：什么是物化路径？**
A：在节点上存一条从根到自身的路径串，如 `/1/4/9/`。取子树时用 `path LIKE '/1/4/%'` 前缀匹配，一次查询搞定，不必递归。

**Q：那为什么不直接用递归 CTE 查树？**
A：递归 CTE 每层都要再查一次、受 `cte_max_recursion_depth` 限制，写法也复杂。物化路径把成本移到写入，读取是常数级索引命中。

**Q：移动分类时你们怎么防止产生环？**
A：`CategoryService.update` 里判两件事：新父不能是自己；新父的 `path` 不能以当前节点的 `path` 开头。命中就抛"不能把分类移动到自己的子分类下，会产生环"。

**Q：标签和概念为什么不直接存在条目表里的一个字段？**
A：那是 M:N 联系，必须建关联表。存逗号串违反 1NF、没法建外键和索引，也放不下"标注来源""置信度"这些联系属性。

**Q：条目有哪几个状态？能不能从已归档直接发布？**
A：`DRAFT`/`PENDING`/`PUBLISHED`/`ARCHIVED`。不能，`publish` 明确拒绝 `ARCHIVED`，必须先 `unarchive` 回到草稿。

**Q：为什么发布要校验"有正文或附件"？**
A：防止发布空条目。`publish` 里检查正文为空**且**附件数为 0 时报"条目既无正文也无附件，无法发布"。

**Q：jieba 分词在系统里做什么？**
A：三处——抽关键词、检索高亮、自动概念标注。`tokenize` 用搜索引擎模式，并叠加了一份约 90 词的领域词典避免术语被切碎。

**Q：关键词打分的公式是什么？**
A：`(词频 + min(词长,6)×0.35 + 标题命中1.5 + 领域词2.0) × 类型惩罚`，纯数字乘 0.3，取 Top 8 存进 `kb_item.keywords`。

**Q：为什么要给领域词加权？**
A：纯词频会选出没有区分度的高频词。加 2.0 让"需求获取""等价类划分"这类专业术语浮到前面。

**Q：自动标注是怎么实现的？会不会标错？**
A：`OntologyService.link` 把概念名与别名组成词典，按词长倒序扫描文本，命中即为 `AUTO`（置信度 0.7）。会标错，所以界面允许人工复核，手工标注（1.0）优先且始终保留。

**Q：标签的 `use_count` 怎么维护？会不会不准？**
A：每次保存条目后，`replaceTags` 用 `countGroupByTag()` 把全部标签的使用次数重算一遍，比增量加减更不容易漂移。

**Q：分类的 `item_count` 呢？**
A：条目新建、删除、改分类时由 `adjustCategoryCount()` 增量调整（旧分类 −1、新分类 +1）；另有全量重算入口 `CategoryService.recalculateCounts()` 作为兜底。这里我们踩过一个坑：增量方法一开始定义了却没接到保存路径上，结果新建条目后分类树的数字不更新，后来写脚本对比创建前后的计数才发现并修好。

**Q：列表页同时按标签和概念筛选怎么实现？**
A：标签和概念在关联表里，先分别查出候选条目 id，再作为 `IN` 条件拼到主表查询上（见 `buildSpec`），避免 join 破坏分页。

**Q：软删除和物理删除有什么区别？为什么用软删除？**
A：软删除只置 `kb_item.deleted=1`。因为条目挂着版本快照、检索分块和审计记录，物理删除会连这些可追溯数据一起毁掉。

**Q：N+1 问题你怎么避免的？**
A：`enrichAll` 用 `findByItemIdIn` 一次性批量查类别、作者、标签、概念、附件，再在内存里按 `item_id` 分组分发，把一页 60 次查询压到 5 次。
