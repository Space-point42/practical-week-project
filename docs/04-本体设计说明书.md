## 1 本体的定义与四要素

**本体（Ontology）** 是对某一领域知识的**显式、形式化**描述。它回答的不是「有哪些资料」，
而是「这个领域的知识由哪些概念构成、它们之间是什么关系」。一个本体通常由四要素构成：

| 要素 | 含义 | 本系统中的对应 |
|---|---|---|
| **类（概念）** | 领域中的基本范畴 | `ont_concept` 表，107 个知识点，如「需求分析」「关系代数」 |
| **关系** | 概念之间的语义联系 | `ont_relation_type`（7 种）与 `ont_relation`（183 条三元组） |
| **属性** | 概念自身的特征 | 概念的 `domain`（知识域）、`difficulty`（难度 1~5）、`importance`（重要度 1~5）、`aliases`（别名） |
| **公理** | 领域内的恒真约束 | 层次关系的传递性（若 A 是 B 的子类、B 是 C 的子类，则 A 是 C 的子类）；先修关系的时序约束；对称关系（相关、近义）的无向性 |

本系统的本体服务于三个具体目标：**支撑推理**（如推导学习路径）、**提升检索召回**
（查询扩展）、**降低标注成本**（自动标注与覆盖率度量）。

## 2 建模方法：层次树 + 语义关系双结构

本系统用两种结构共同刻画知识，二者分工明确、互补而非替代：

| 结构 | 表达方式 | 回答的问题 | 存储 |
|---|---|---|---|
| **层次树（taxonomy）** | `parent_id`（邻接表）+ `path`（物化路径） | 「这个知识点属于哪一类」 | `ont_concept.parent_id`、`ont_concept.path` |
| **语义关系（网络）** | 三元组 `(源概念, 关系类型, 目标概念)` | 「这个知识点与其它知识点是什么关系」 | `ont_relation` |

**为什么用双结构？** 仅有层次树，知识是彼此孤立的分类标签——「关系代数」与「SQL 查询」
可能分属不同的树枝，树上看不出它们的关系；加上语义关系，才能形成**可推理的网络**。
反过来，仅有语义关系而无层次，则知识缺少宏观的组织骨架，用户在浏览时无处落脚。

两者在实现上也互相衔接：**层次结构在初始化时自动转换为 `SUB_CLASS_OF` 关系**，
把「分类树」纳入本体语义网络。具体做法是遍历概念种子数据，对每个有父节点的概念生成一条
`(子概念, SUB_CLASS_OF, 父概念, 权重 0.95)` 的三元组。这解释了关系实例的构成：
107 个概念中有 104 个非根概念，恰好生成 **104 条层次关系**，其余 79 条为人工标注的领域语义关系。

```
                    本体 = 层次树（骨架） + 语义关系（网络）
   ┌──────────────────────────────┐     ┌──────────────────────────────┐
   │ 自动生成 104 条 SUB_CLASS_OF  │  +  │ 人工标注 79 条领域语义关系     │
   └──────────────────────────────┘     └──────────────────────────────┘
                     ↓                                  ↓
              共 183 条关系实例（7 种关系类型）
```

## 4 七种关系类型

本系统定义 **7 种语义关系**（远超任务书要求的 5 种），编码、逆关系、有向性与语义如下。
配色取自通过色觉缺陷可辨识性校验的色板（相邻色对在色觉缺陷模拟下 ΔE ≥ 9，正常视觉 ΔE ≥ 19），
且图谱中的边同时带文字标签，使关系类型的识别不依赖颜色单一通道。

| 编码 | 中文名 | 逆关系 | 有向 | 配色 | 语义 | 示例三元组 |
|---|---|---|---|---|---|---|
| `SUB_CLASS_OF` | 上下位（is-a） | `SUPER_CLASS_OF` | 是 | `#2a78d6` | 子概念是父概念的一种特化，**传递关系** | （单元测试, `SUB_CLASS_OF`, 软件测试） |
| `PART_OF` | 组成（part-of） | `HAS_PART` | 是 | `#eb6834` | 部分与整体的构成关系 | （需求获取, `PART_OF`, 软件需求） |
| `PREREQUISITE_OF` | 先修 | `DEPENDS_ON` | 是 | `#1baf7a` | 学习顺序上的前置依赖，**用于推导学习路径** | （关系代数, `PREREQUISITE_OF`, 结构化查询语言） |
| `RELATED_TO` | 相关 | `RELATED_TO` | 否 | `#eda100` | 语义相关但无严格从属，**对称关系**，用于知识导航与查询扩展 | （配置管理, `RELATED_TO`, 版本管理） |
| `APPLIED_IN` | 应用于 | `APPLIES` | 是 | `#e87ba4` | 理论、方法被应用到某个实践环节 | （倒排索引, `APPLIED_IN`, 全文检索） |
| `PRODUCES` | 产出 | `PRODUCED_BY` | 是 | `#008300` | 某活动产生的制品 | （概念结构设计, `PRODUCES`, 实体联系模型） |
| `SYNONYM_OF` | 近义/别名 | `SYNONYM_OF` | 否 | `#4a3aa7` | 概念的不同表述方式，**对称关系**，用于实体链接时的同义归一 | （全文检索, `SYNONYM_OF`, 倒排索引） |

> **逆关系说明：** 有向关系的逆关系编码用于图谱的反向遍历与推理；对称关系（`RELATED_TO`、
> `SYNONYM_OF`）的逆关系与自身相同，`directed = 0`。

> 每条关系实例都带有**权重**（`weight`，0~1，`DECIMAL(4,2)`）与**自然语言断言**

> `(关系代数, PREREQUISITE_OF, 结构化查询语言, 0.9, "关系代数是理解 SQL 查询语义的理论基础")`。

### 5.2 典型三元组

| 关系类型 | 三元组 | 权重 | 说明 |
|---|---|---|---|
| `PREREQUISITE_OF` | 关系模型 → 关系代数 | 0.85 | 先建立关系模型的概念再学习关系运算 |
| `PREREQUISITE_OF` | 函数依赖 → 规范化理论 | 0.95 | 先掌握函数依赖才能判断范式 |
| `PREREQUISITE_OF` | 软件需求 → 软件设计 | 0.95 | 需求是设计的输入 |
| `PART_OF` | 需求分析 → 软件需求 | 0.9 | 需求分析是需求工程的一个环节 |
| `APPLIED_IN` | 规范化理论 → 逻辑结构设计 | 0.9 | 规范化理论用于优化逻辑模式 |
| `PRODUCES` | 需求分析 → 需求规格说明 | 0.9 | 需求分析产出需求规格说明书 |
| `RELATED_TO` | 知识图谱 ↔ 知识本体建模 | 0.9 | 知识图谱是本体的实例化与可视化 |
| `SYNONYM_OF` | 全文检索 ↔ 倒排索引 | 0.4 | 全文检索的实现几乎总是基于倒排索引 |

### 5.3 防重复机制

`ont_relation` 表在 `(source_id, target_id, relation_type)` 上建立唯一键 `uk_relation_triple`，
种子导入时另有内存去重集合，保证同一三元组不重复。这避免了「同一关系被记两次、图谱上出现
平行边」的问题。

## 6 本体推理

本系统支持沿**指定关系类型**从起点概念逐层展开推理（`OntologyService.infer`），
最大深度可配（1~5 层），并返回每一层到达的概念与路径说明。

### 6.1 沿先修关系推导学习路径（真实存在的路径）

以「关系模型」为起点、沿 `PREREQUISITE_OF` 展开 3 层：

```text
起点：关系模型（DB.MODEL.RELATIONAL）
  │
  ├─ 第 1 层：关系代数（DB.THEORY.ALGEBRA）          ← 关系模型 -[先修]-> 关系代数
  │
  ├─ 第 2 层：结构化查询语言（DB.SQL）               ← 关系代数 -[先修]-> SQL
  │
  └─ 第 3 层：索引与查询优化（DB.SQL.INDEX）         ← SQL -[先修]-> 索引与查询优化
```

这条路径由 `PREREQUISITE_OF` 三元组自动推导：
`(关系模型, PREREQUISITE_OF, 关系代数)`、`(关系代数, PREREQUISITE_OF, SQL)`、
`(SQL, PREREQUISITE_OF, 索引与查询优化)`。它给出的是一条**有依据的学习顺序**，
而非人工排定的顺序。

### 6.2 沿先修关系推导的另一条路径

```text
需求获取（SE.REQ.ELICITATION）
  → 需求分析（SE.REQ.ANALYSIS）          ← 先获取需求再做分析
  → 需求规格说明（SE.REQ.SPEC）          ← 分析结果是规格说明的素材
```

### 6.3 沿组成关系推导知识结构

沿 `PART_OF` 从「数据库设计」展开，可得到其三个阶段的组成结构：
概念结构设计、逻辑结构设计、物理结构设计——这正是《数据库原理》中数据库设计三阶段方法
在本体中的体现。

> 推理在界面上的对应：知识图谱页支持「只显示某一种关系」（如只看先修关系即得学习路径），
> 并提供推理展开功能；测试用例 TC-ONT-02 / TC-ONT-05 对其进行了验证。

## 7 实体链接算法

**实体链接（Entity Linking）** 指从一段自然语言文本中识别出所涉及的本体概念。
本系统采用「**长词优先的词典扫描 + 别名归一**」的朴素但有效的算法
（`OntologyService.link`）：

| 步骤 | 做法 | 目的 |
|---|---|---|
| 1. 构建词典 | 把每个概念的**名称**、**英文名**、**别名**（`aliases`，逗号分隔）都作为一个词条加入词典，都指向同一概念 | **别名归一**：使「SRS」与「需求规格说明书」映射到同一概念 |
| 2. 排序 | 词典按词条**长度倒序**排列 | **长词优先**：先匹配「需求分析」再匹配「需求」，避免短词抢占 |
| 3. 扫描 | 对输入文本做小写化后进行子串包含判断，命中即记录其概念 | 简单、稳定、无外部依赖 |
| 4. 去重截断 | 按概念 id 去重，返回不超过 `limit` 个概念 | 结果有序、可控 |

**示例：** 输入「软件测试与需求分析的关系」→ 依据长词优先规则，先匹配到「需求分析」与
「软件测试」，而不会被更短的「需求」抢先；输出概念集合：软件测试、需求分析。

实体链接是三项能力的基础：**自动标注**（为条目自动挂知识点）、**查询扩展**（检索与问答）、
**RAG 上下文增强**。

## 8 查询扩展

**查询扩展**指在检索前利用本体把用户的查询串增强，以弥补「用户用词与文档用词不一致」
造成的召回损失。本系统的扩展发生在 RAG 问答与检索的查询构造阶段
（`RagService.expandQuery` / `OntologyService.expand`）：

1. 先对用户问题做**实体链接**，识别命中的知识点（最多 8 个）；
2. 沿本体关系扩展相邻概念，**允许参与扩展的关系类型为**：

   | 关系类型 | 扩展含义 |
   |---|---|
   | `SUB_CLASS_OF` | 上下位：加入父/子概念，泛化或特化查询 |
   | `PART_OF` | 组成：加入整体或部分，补全结构语境 |
   | `PREREQUISITE_OF` | 先修：加入前置知识点，补全学习脉络 |
   | `RELATED_TO` | 相关：加入语义相邻概念 |
   | （层次结构直接父/子节点） | 保证层次上的相邻知识点也能被召回 |

   > 注：`APPLIED_IN`、`PRODUCES`、`SYNONYM_OF` **不参与**扩展——前三类关系的语义距离较远
   > 或已被别名归一吸收，加入反而引入噪声。扩展上限为 6 个概念（`ontology-expand-limit`）。

3. 把扩展出的概念名拼到查询串尾部，形成增强检索串。因为两条召回通道（向量通道按词面特征、
   关键字通道按 ngram 词项）都直接读取该检索串，**两条通道同时受益**。

**示例：** 用户问「需求分析怎么做」——
- 实体链接命中「需求分析」；
- 沿先修/组成关系扩展出「需求获取」「需求验证」「需求规格说明」等；
- 检索串变为「需求分析怎么做 需求获取 需求验证 需求规格说明」；
- 于是相邻知识点下的资料也被召回。

在术语密集的课程语料上，这一步能**额外召回 20%~40% 的相关条目**（见系统内《RAG 检索增强
问答的设计与实现》一文的实测说明）。测试用例 TC-RAG-01 断言检索元数据中的
`expandedConcepts` 非空，验证该能力生效。

## 9 本体覆盖率与内容缺口

**本体覆盖率**定义为：**已被至少一条知识条目标注过的知识点**占全部知识点的比例。

```text
覆盖率 = 被标注过的知识点数 / 知识点总数 × 100%
```

实现上由 `OntologyService.stats()` 计算：`covered = 标注关联表中出现的不同概念数`，
`coverage = covered / 概念总数`（保留两位小数）。在本系统的演示数据上，覆盖率为 **93.46%**。

**覆盖率的两个用途：**

1. **度量知识库的完整度**——覆盖率越高，说明知识库对有结构的课程知识体系的覆盖越充分；
2. **暴露内容缺口**——未被任何条目标注的知识点即为「知识库尚未覆盖的空白」，可指导后续
   补充内容。在「知识点管理」与「本体统计」页面按覆盖率排序，即可直观看到哪些知识点还没有
   配套资料。

未被覆盖的知识点通常是**长尾或高阶概念**（例如 `DB.NEW.DISTRIBUTED` 分布式数据库、
`SE.MAINT.REENGINEER` 软件再工程），这与课程内容的重心相符，属于合理的覆盖分布。

## 10 本体与「分类」的区别

本系统同时维护**分类（`kb_category`）**与**本体（`ont_concept`）**两套结构，二者视角不同、
互为补充，不是重复设计：

| 对比维度 | 分类（Category） | 本体（Ontology） |
|---|---|---|
| 视角 | **管理视角**：内容归谁管、放在哪里 | **知识视角**：知识由什么构成、彼此什么关系 |
| 结构 | 一棵分类树（每篇内容挂一个分类） | 概念层次树 **+** 语义关系网络 |
| 粒度 | 较粗（如「技术报告 / 设计文档」） | 较细（如「逻辑结构设计」「函数依赖」） |
| 内容关系 | 一个条目挂**一个**分类 | 一个条目可标注**多个**知识点 |
| 是否可推理 | 否 | 是（沿先修、组成等关系推导） |
| 是否携带语义 | 仅层次归属 | 携带 7 种语义关系与权重 |
| 主要用途 | 浏览导航、权限与统计 | 检索召回、自动标注、学习路径、覆盖率度量 |
| 数据表 | `kb_category` | `ont_concept` / `ont_relation_type` / `ont_relation` |
| 变化频率 | 稳定，偶尔调整 | 相对活跃，随知识体系细化而演进 |

**一句话区分：** 分类回答「这篇资料**归在哪一格**」，本体回答「这篇资料**涉及哪些知识、
这些知识之间是什么关系**」。前者服务于**找得到**，后者服务于**看得懂、联得起来**。
